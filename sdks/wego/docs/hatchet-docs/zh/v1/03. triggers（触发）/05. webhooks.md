# Webhook

Webhook 允许外部系统通过向专用端点发送 HTTP 请求来触发 Hatchet workflow。这使得与 GitHub、Stripe、Slack 等第三方服务，或任何能够发送 webhook 事件的系统进行实时集成成为可能。

## 指南

我们为最常见的 webhook 集成提供了分步指南：

- [**Stripe**](<../../cookbooks/07. webhooks-stripe.md>) —— 支付、订阅、发票
- [**GitHub**](<../../cookbooks/08. webhooks-github.md>) —— pull request、issue、push
- [**Slack**](<../../cookbooks/09. webhooks-slack.md>) —— 斜杠命令、交互组件、事件订阅

## 创建 webhook

创建 webhook 时，你需要填写一些字段，告诉 Hatchet 如何确定从该 webhook 触发哪些 workflow，以及如何在请求到达时验证它。具体而言，你需要提供以下字段：

#### 名称

**Webhook Name** 在租户内唯一（即单个租户中每个名称只能使用一次），用于生成传入 webhook 请求的发送 URL。例如，如果你的租户 ID 是 `d60181b7-da6c-4d4c-92ec-8aa0fc74b3e5`，webhook 名称是 `my-webhook`，那么 URL 可能类似于 `https://cloud.onhatchet.run/api/v1/stable/tenants/d60181b7-da6c-4d4c-92ec-8aa0fc74b3e5/webhooks/my-webhook`。注意，你可以在仪表板中复制此 URL。

#### 来源

**Source** 表示 webhook 的来源，可以是便于快速设置的预置来源（如 Stripe 或 Github），也可以是 "generic"（通用）来源 —— 它允许你根据 webhook 发送方提供的信息配置集成所需的全部字段。

#### 事件键表达式

**Event Key Expression** 是一个 [CEL](<../05. flow-control（流控）/06. cel-expressions.md>) 表达式，你可以用它根据传入 webhook 的载荷和头部生成动态事件键。你可以将其设为常量值（如 `webhook`），也可以利用这两个来源设为动态值。一些示例：

1. `'stripe:' + input.type` 会生成以 `'stripe:'` 为前缀的事件键（表明 webhook 来自 Stripe），`input.type` 取 webhook 载荷中的 `type` 字段来生成最终事件键。结果可能类似于 `stripe:payment_intent.created`。
2. `'github:' + headers['x-github-event'] + ':' + input.action` 可以生成类似 `github:star:created` 的键

> **Info:** 事件键表达式的结果就是 Hatchet 使用的事件键，因此你需要在 workflow 上
>   设置匹配的事件键作为触发器，才能通过创建的 webhook 触发它们。例如，在前面的
>   示例中，你可以添加 `on_events=["stripe:payment_intent.created"]` 来监听
>   payment intent created 事件。

#### 作用域表达式（可选）

**Scope Expression** 是一个可选的 [CEL](<../05. flow-control（流控）/06. cel-expressions.md>) 表达式，其结果是一个字符串，用于筛选要触发的 workflow。当你有多个 workflow 监听同一个事件键，但希望根据 webhook 内容路由到特定 workflow 时，这很有用。

与事件键表达式一样，你可以访问 `input`（webhook 载荷）和 `headers`（请求头）。一些示例：

1. `input.customer_id` 会使用载荷中的客户 ID 作为作用域
2. `headers['x-organization-id']` 会使用某个头部值作为作用域
3. `input.metadata.environment` 可以根据环境路由到不同的 workflow

#### 静态载荷（可选）

**Static Payload** 是一个可选的 JSON 对象，会在传入的 webhook 载荷传给你的 workflow 之前与其合并。这适用于：

- 为该 webhook 的所有事件添加固定元数据
- 注入原始载荷中没有的配置值
- 覆盖传入载荷中的特定字段

> **Info:** 当传入的 webhook 载荷与静态载荷的键冲突时，静态载荷的值优先。

例如，如果你设置静态载荷为 `{"source": "stripe", "environment": "production"}`，并收到载荷为 `{"type": "payment_intent.created", "source": "api"}` 的 webhook，那么传给你的 workflow 的最终载荷将是 `{"type": "payment_intent.created", "source": "stripe", "environment": "production"}`。

#### 身份认证

最后，你需要指定 Hatchet 应如何对传入的 webhook 请求进行身份认证。对于 Stripe 和 Github 等非通用来源，Hatchet 已为大多数字段预置了配置，因此在大多数情况下你只需提供密钥（secret）。

如果使用通用来源，你需要指定认证方式（basic auth、API key 或基于 HMAC 的认证），并提供所需的字段（例如 basic auth 情况下的用户名和密码）。

> **Warning:** Hatchet 会对你在验证传入 webhook 时提供的任何密钥进行加密。

不同的认证方式需要提供不同的字段：

- **预配置来源**（Stripe、GitHub、Slack）：只需提供 webhook secret
- **通用来源**根据所选认证方式需要不同字段：
  - **Basic Auth**：需要用户名和密码
  - **API Key**：需要包含密钥的请求头名称，以及密钥本身
  - **HMAC**：需要包含密钥的请求头名称、密钥本身、编码方式（如 hex、base64）和算法（如 `SHA256`、`SHA1` 等）。

## 使用

在创建 webhook 的过程中（以及创建之后），你可以复制 webhook URL，它就是你要提供给 webhook *发送方* 的地址。

完成之后，最后一步是注册你希望 worker 监听的事件键，使其能够被传入的 webhook 触发。

具体做法示例请参阅[事件触发器文档](<04. events.md#declaring-event-triggers>)。
