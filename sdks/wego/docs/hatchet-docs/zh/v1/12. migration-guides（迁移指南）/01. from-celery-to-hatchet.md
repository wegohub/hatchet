# 从 Celery 迁移到 Hatchet

Celery 是一个成熟且广泛使用的后台任务系统。本指南假设你已经决定将一个 Python 项目从 Celery 迁移到 Hatchet，并希望了解需要更改哪些代码和配置。每一节都从一个常见的 Celery 模式开始，然后展示它在 Hatchet 中的替代方案以及需要注意的事项。

> **Info:** 本指南覆盖常见的 Celery 模式，不覆盖每一个 Celery 设置，也不试图
>   进行完整的基础设施迁移。关于 Celery 运维权衡的讨论，请参阅
>   [这篇博文](https://hatchet.run/blog/problems-with-celery)。

## 步骤 1：更新依赖和运行时配置

### 依赖

使用你选择的包管理器在 Celery 之外安装 `hatchet-sdk`。例如：

```bash
pip install hatchet-sdk
```

迁移期间 Celery 和 Hatchet 可以并行运行。这让你可以一次一个地将 Celery task 迁移到 Hatchet，并逐步验证行为。由于 Celery 和 Hatchet 不共享工作流运行时，每个迁移的 task 或 workflow 必须有清晰的边界。一旦某个 task 或 workflow 被迁移到 Hatchet，就更新将其入队的应用代码，使其调用 Hatchet 而不是 Celery。

### 配置

Celery 项目会配置 broker 和 result backend 连接。Hatchet 没有对应的 broker 或 result-backend 设置。取而代之，你需要配置 Hatchet SDK 使其能够连接到 Hatchet 引擎。对于 [Hatchet Cloud](https://cloud.onhatchet.run)，用 API token 配置 SDK：

```bash
export HATCHET_CLIENT_TOKEN="your-token-here"
```

对于[自托管](<../01. get-started（入门）/01. index.md>)或本地 Hatchet 部署，你可能需要针对 Hatchet 引擎端点和 TLS 配置的环境特定的客户端设置。

Celery 的默认加载器从 Python 路径上的 `celeryconfig.py` 模块读取设置。框架集成可能从其他来源加载相同的设置；例如 Django 项目通常通过 `CELERY_` 命名空间从 Django settings 加载 Celery 设置。完整列表请参阅 [Celery 配置参考](https://docs.celeryq.dev/en/stable/userguide/configuration.html)。如果你的项目有大量 Celery 配置，请逐节审阅本指南，确定哪些设置需要迁移、哪些可以删除。

### 进程和部署清理

Celery 项目通常运行多个长驻进程，包括 worker、名为 Celery Beat 的任务调度器，以及可选的用于运行时监控的 Flower。视环境而定，它们可能由 init 脚本、systemd 服务、supervisor、launchd、Docker Compose、Kubernetes 清单、`Procfile` 或 CI/部署脚本管理。Celery 的[守护进程化文档](https://docs.celeryq.dev/en/stable/userguide/daemonizing.html)提供了管理这些进程的指导，是理解现有部署的有用资源。

用 Hatchet 的 [worker 脚本](#step-5-run-a-hatchet-worker)替换 Celery worker 和 Beat 进程。Hatchet 的 cron run 由 Hatchet 引擎管理，因此无需部署单独的调度器进程。Hatchet 的控制台取代了基本的 Flower 部署，提供运行时可见性。

Broker 和 result backend 服务是另一个独立的清理步骤。不要仅因为要移除 Celery 就删除 Redis、RabbitMQ、SQS、SQL 数据库、Cassandra 等基础设施。只有在确认它们仅被 Celery 使用、且应用不再使用之后，才移除或下线这些服务。

## 步骤 2：用 Hatchet 客户端替换 Celery 应用

Celery 项目通常有一个共享的 `Celery` 应用实例，用于定义 broker、result backend 和任务注册表。在 Hatchet 中，用共享的 `Hatchet` 客户端替换该共享应用对象。

**Celery：**

```python
from celery import Celery

app = Celery("tasks", broker="redis://localhost:6379", backend="redis://localhost:6379")
```

**Hatchet：**

```python
from hatchet_sdk import Hatchet

hatchet = Hatchet()
```

`Hatchet()` 客户端默认从 `HATCHET_CLIENT_*` 环境变量（包括 `HATCHET_CLIENT_TOKEN`）读取 SDK 配置。在共享模块中创建 `Hatchet` 实例，并在任何需要与 Hatchet 交互的代码中导入它。

对于自托管或本地部署，你可能需要额外的客户端配置，例如 Hatchet API 端点、gRPC 主机或 TLS 设置。这些可以通过环境变量提供，SDK 在需要时也支持显式的[客户端配置](<../../reference/15. client.md>)。

变化点：

- **共享应用对象变了。** 用共享的 `hatchet = Hatchet()` 客户端替换共享的 Celery `app = Celery(...)` 实例。
- **Broker 和 backend 设置移出应用构造函数。** Hatchet 不接受 Celery 风格的 `broker=` 或 `backend=` 参数。
- **连接设置移入 SDK 配置。** 使用 `HATCHET_CLIENT_*` 环境变量，或在需要时使用显式客户端配置。
- **迁移期间复用同一个客户端。** 在定义 task、workflow、worker 以及触发 run 的代码中导入共享的 `hatchet` 客户端。

## 步骤 3：转换 task 定义

Celery task 接受可选的任务级参数。在 Hatchet 中，[task 函数](<../02. core-concepts（核心概念）/01. tasks.md>)接收一个输入对象和一个 context 对象，而不是位置参数。

**Celery：**

```python
from celery import Celery

app = Celery("tasks", broker="redis://localhost:6379")

@app.task
def process_image(image_url: str, filters: list[str]) -> dict:
    result = resize(image_url, filters)
    return {"processed_url": result}
```

要迁移这个 Celery task，需要为 `image_url` 和 `filters` 定义一个输入模型，把装饰器改为 `@hatchet.task(...)`，添加 `ctx: Context`，并返回一个可序列化的 task 输出。

**Hatchet：**

```python
@hatchet.task(name="process-image", input_validator=ImageInput)
async def process_image(input: ImageInput, ctx: Context) -> ImageOutput:
    result = await resize(input.image_url, input.filters)
    return ImageOutput(processed_url=result)
```

变化点：

- **`@app.task` 变成 `@hatchet.task(...)`。** 使用 `input_validator=YourModel` 验证并为 task 输入提供类型。
- **位置参数移入输入模型。** 把 `(image_url, filters)` 替换为 `input: ImageInput`，其中 `ImageInput` 是包含这些字段的 Pydantic `BaseModel`。
- **task 接收一个 context 对象。** 添加 `ctx: Context` 作为第二个参数，用于获取 run 元数据、重试信息、父 task 输出和日志。
- **返回值即 task 输出。** 返回一个 Pydantic 可以序列化的值，例如 Pydantic 模型或 dict。
- **task 可以是同步或异步的。** Hatchet task 可以是 `def` 或 `async def`；对于 I/O 密集型工作，SDK [推荐 async](<../../reference/18. asyncio.md>)。

> **Warning:** 如果你的 Celery task 使用位置参数、`*args` 或 `**kwargs`，你需要
>   定义一个捕获预期字段的 Pydantic 模型。对于不接收有意义输入的 task，
>   使用 `hatchet_sdk` 中的 `EmptyModel`。这种输入模型转换是迁移中主要的
>   机械性工作量所在。

### 序列化

Celery 通过 `task_serializer` 支持 JSON、pickle、YAML 和 msgpack 等序列化器。Hatchet 的 [task 输入和输出](<../02. core-concepts（核心概念）/01. tasks.md#input-and-output>)通过 Pydantic 序列化。如果你的 Celery 项目使用 `pickle` 或其他非 JSON 序列化器，请确保你的 task payload 能够以 Pydantic 的 [JSON 序列化模式](https://pydantic.dev/docs/validation/latest/concepts/serialization/#json-mode)表示。Pydantic 无法直接序列化的值应转换为 JSON 兼容的字段，或使用自定义 Pydantic 序列化器处理。

## 步骤 4：用输入模型调用 task

在 Celery 中，被 `@app.task` 装饰的函数通过 Celery 的任务调用 API 调用。`.delay(...)` 等调用把参数传给底层 task 函数，而 `apply_async(...)` 通过 `args=` 和 `kwargs=` 传递。在 Hatchet 中，用你在步骤 3 中定义的输入模型调用 task。无论等待结果还是入队后继续，使用的都是同一个 task 输入模型。

**Celery：**

```python
# Fire-and-forget
process_image.delay("https://example.com/photo.png", ["thumbnail"])

# With options
process_image.apply_async(
    args=["https://example.com/photo.png", ["thumbnail"]],
)
```

要迁移这些调用，把 task 参数替换为 `ImageInput(...)`，并在 Hatchet task 上调用 `.run()` 或 `.aio_run()`。默认情况下，Hatchet 会等待 task 完成并直接返回类型化的结果。

**Hatchet：**

```python
async def run_image_task() -> None:
    # Wait for the result (default behavior)
    result = await process_image.aio_run(
        ImageInput(image_url="https://example.com/photo.png", filters=["thumbnail"]),
    )
    print(result.processed_url)

    # Fire-and-forget: enqueue without waiting
    ref = await process_image.aio_run(
        ImageInput(image_url="https://example.com/photo.png", filters=["thumbnail"]),
        wait_for_result=False,
    )
    print(ref.workflow_run_id)  # available immediately
    # await ref.aio_result() to retrieve the result later
```

变化点：

- **task 参数移入输入模型。** 把诸如 `("https://example.com/photo.png", ["thumbnail"])` 的 task 参数替换为 `ImageInput(image_url=..., filters=...)`。
- **调用方法变了。** 用 `.run()`（同步代码）或 `.aio_run()`（异步代码）替换 `.delay()` / `.apply_async()`。
- **默认调用会等待结果。** Celery 的 `.delay()` 将工作入队并立即返回 `AsyncResult`。Hatchet 的 `.run()` 和 `.aio_run()` 会等待 task 完成并直接返回类型化的结果。
- **Fire-and-forget 使用 `wait_for_result=False`。** 要入队而不等待，传入 `wait_for_result=False`。它返回一个 `TaskRunRef`，其中包含 run ID 以及稍后可调用的 `.result()` / `.aio_result()` 方法。
- **延迟执行使用单独的 API。** 用 scheduled run 替换 Celery 的 `countdown` 或 `eta`，详见[步骤 7](#step-7-migrate-delayed-and-periodic-tasks)。

## 步骤 5：运行 Hatchet worker

Celery worker 通常通过 CLI 或进程管理器启动：

**Celery：**

```bash
celery -A tasks worker --loglevel=info --concurrency=4
```

在 Hatchet 中，迁移产物是一个显式注册其可执行 task 和 workflow 的 Python worker 脚本：

**Hatchet：**

```python
def start_worker() -> None:
    worker = hatchet.worker("image-worker", slots=4, workflows=[process_image])
    worker.start()
```

开发期间，用 [Hatchet CLI](<../../reference/06. running-workers-locally.md>) 启动 worker，它会处理认证并在代码变更时热重载：

```bash
hatchet worker dev
```

生产环境中，在设置好 `HATCHET_CLIENT_TOKEN` 的情况下直接运行 worker 脚本：

```bash
python worker.py
```

变化点：

- **worker 以代码方式定义。** 用在 worker 的 `workflows=[...]` 列表中注册可执行 task 和 workflow 的 worker 脚本，替换 Celery 基于应用的 task 自动发现。
- **worker 容量移至 `slots`。** 用 Hatchet worker 的 `slots` 参数替换 Celery 的 `--concurrency=4` 标志。
- **启动方式因环境而异。** 本地开发时使用 `hatchet worker dev`，生产环境中通过进程管理器或容器运行时运行 worker 脚本。
- **Celery pool 设置不能直接迁移。** Celery 支持 prefork、eventlet、gevent、threads 等 pool 类型。Hatchet Python worker 使用 SDK 的同步/异步执行模型和 worker slot，因此 CPU 密集型工作可能需要线程、子进程或独立的 worker。

## 步骤 6：迁移重试和超时

### 重试

Celery 支持针对指定异常类型的自动重试，以及 task 体内的手动重试。

**Celery：**

```python
# Automatic: retry only on RequestError, with exponential backoff
@app.task(bind=True, autoretry_for=(RequestError,),
          retry_backoff=True, max_retries=5, retry_backoff_max=60)
def call_api(self, order_id: str) -> dict:
    return external_api_call(order_id)

# Manual: explicit retry with custom logic
@app.task(bind=True, max_retries=3)
def call_api_manual(self, order_id: str) -> dict:
    try:
        return external_api_call(order_id)
    except RequestError as exc:
        raise self.retry(exc=exc, countdown=30)
```

要迁移自动重试，把重试策略移到 Hatchet task 装饰器上。配置了 retries 后，Hatchet 会在 task 失败时重试，因此通过抛出普通异常来表示可重试的失败即可。

**Hatchet：**

```python
@hatchet.task(
    name="call-api",
    retries=5,
    backoff_factor=2.0,
    backoff_max_seconds=60,
    execution_timeout=timedelta(seconds=30),
    input_validator=OrderInput,
)
async def call_api(input: OrderInput, ctx: Context) -> dict[str, str]:
    result = await external_api_call(input.order_id)
    return {"status": result}
```

要防止已知的永久性失败被重试，可在 task 体内抛出 `NonRetryableException`：

```python
from hatchet_sdk.exceptions import NonRetryableException

# Inside a task: skip retry for a permanent failure
if response.status_code == 400:
    raise NonRetryableException("Bad request: do not retry")
```

完整的重试选项和行为请参阅[重试策略](<../04. reliability（可靠性）/01. retry-policies.md>)。

变化点：

- **重试策略移到 task 装饰器上。** 用 Hatchet 的 `retries`、`backoff_factor` 和 `backoff_max_seconds` 替换 Celery 的 `max_retries`、`retry_backoff`、`retry_backoff_max` 等重试选项。
- **审查重试异常规则。** Celery 的 `autoretry_for=(...)` 列出应触发重试的异常。在 Hatchet 中，只要 `retries > 0`，task 失败即可重试；对于不应重试的失败，抛出 `NonRetryableException`。
- **手动 `self.retry()` 逻辑需要重新设计。** Hatchet 在 task 体内没有直接的 `self.retry()` 等价物；task 级别的重试行为由 Hatchet 引擎管理。

### 超时

**Celery：**

```python
@app.task(time_limit=30, soft_time_limit=25)
def long_task():
    ...
```

除非配置，Celery 默认不设置 task 时间限制。Hatchet 使用 [`execution_timeout`](<../04. reliability（可靠性）/02. timeouts.md>) 控制 task 最长可运行时间，用 `schedule_timeout` 控制 task 在队列中最长可等待多久后被取消。就迁移而言，Hatchet 的 `execution_timeout` 与 Celery 的 `time_limit` 最接近。Celery 的 `soft_time_limit` 没有精确的 Hatchet 等价物。如果你的 task 依赖软超时做清理，请在迁移期间把清理逻辑改写为显式的 task 逻辑。

**Hatchet：**

```python
from datetime import timedelta

@hatchet.task(execution_timeout=timedelta(seconds=30))
async def long_task(input, ctx):
    ...
```

变化点：

- **硬性任务限制移至 `execution_timeout`。** 用 `execution_timeout=timedelta(seconds=30)` 替换 Celery 的 `time_limit=30`。
- **队列等待时间单独控制。** Hatchet 的 `schedule_timeout` 控制 task 在队列中最多等待多久后被取消。
- **软超时清理必须重写。** Celery 的 `soft_time_limit` 没有精确的 Hatchet 等价物，依赖软超时异常的清理应改为显式的 task 逻辑。
- **审查超时默认值。** Celery 的 task 时间限制默认不启用；Hatchet 有默认超时行为，依赖隐式行为前请先查阅超时文档。

## 步骤 7：迁移延迟任务和周期任务

### 延迟执行

在 Celery 中，延迟执行在调用点通过 `apply_async` 的 `countdown` 或 `eta` 配置：

```python
# Run 5 minutes from now
process_image.apply_async(args=["https://example.com/photo.png", ["blur"]], countdown=300)

# Run at a specific time
from datetime import datetime, timedelta, timezone
process_image.apply_async(
    args=["https://example.com/photo.png", ["blur"]],
    eta=datetime.now(timezone.utc) + timedelta(hours=1),
)
```

> **Warning:** Celery 文档
>   [警告](https://docs.celeryq.dev/en/stable/userguide/calling.html#eta-and-countdown)
>   ETA/countdown 任务在被调度执行之前会一直保存在 worker 内存中，并建议
>   只使用较短的延迟，而不要调度到太远的将来。

把这些调用点迁移到 Hatchet 时，延迟执行改用 scheduled run API。Scheduled run 由 Hatchet 引擎持久化，而不是保存在 worker 内存中，因此更长的延迟变得可行：

```python
async def schedule_for_later() -> None:
    from datetime import datetime, timezone

    run_at = datetime.now(tz=timezone.utc) + timedelta(hours=1)
    await process_image.aio_schedule(
        run_at,
        ImageInput(image_url="https://example.com/photo.png", filters=["blur"]),
    )
```

变化点：

- **`countdown` / `eta` 变为 scheduled run。** 用 `task.aio_schedule(run_at, input)` 替换 `apply_async(..., countdown=...)` 或 `apply_async(..., eta=...)`。
- **task 输入形状保持不变。** Scheduled run 使用与立即执行的 `.aio_run(...)` 相同的 `ImageInput(...)` 模型。
- **worker 不再持有延迟。** Hatchet 将 scheduled run 持久化在引擎中，直到可以执行。

### 周期任务

在 Celery 中，周期性调度通常定义在 `beat_schedule` 中，由独立的 Celery Beat 进程执行：

```python
# celeryconfig.py
from celery.schedules import crontab

beat_schedule = {
    "daily-report": {
        "task": "tasks.generate_report",
        "schedule": crontab(hour=9, minute=0),
    },
}
```

生产环境中，Beat 可能通过进程管理器、容器运行时或直接从 CLI 运行：

```bash
celery -A tasks beat  # must run exactly one instance
```

在 Hatchet 中，[cron 触发器](<../03. triggers（触发）/02. cron-runs.md>)通过 `on_crons` 参数声明在 task 上，它接受一个由 Hatchet 引擎管理的 cron 表达式列表。把周期任务迁移到 Hatchet 时，将使用 Celery `crontab(...)` 辅助函数的 Beat 调度转换为 `on_crons` 条目：

```python
@hatchet.task(name="DailyReport", on_crons=["0 9 * * *"])
async def generate_report(input: EmptyModel, ctx: Context) -> dict[str, str]:
    await build_report()
    return {"status": "sent"}
```

变化点：

- **Celery Beat 被移除。** 你不再运行独立的 `celery beat` 进程，也不必确保只有一个 Beat 实例在运行。
- **调度计划移到 task 上。** 用 `on_crons=["0 9 * * *"]` 替换 `beat_schedule` 条目。
- **Celery 的 `crontab(...)` 变为 cron 表达式。** 使用标准的 5 字段或 6 字段 cron 语法。
- **非 crontab 调度需要审查。** Interval、solar 或自定义 Beat 调度可能无法直接转换为 cron 表达式。
- **运行时调度管理移至 cron 客户端。** 如果你的应用动态创建、列出或删除调度计划，请使用 [`hatchet.cron` 客户端](<../../reference/24. cron.md>)。

## 步骤 8：迁移 chain、group 和 chord

这是迁移中最大的概念性变化。Celery Canvas 在_调用点_构建任务。相比之下，Hatchet DAG workflow 在 workflow 定义中预先声明依赖图。理解 Hatchet 的[工作流编排模型](<../../cookbooks/06. durable-tasks-vs-dags.md>)会让本节其余部分更容易理解。

### Celery chain 到 Hatchet DAG

**Celery：**

```python
from celery import chain

pipeline = chain(
    validate.s(order_id),
    charge.s(),
    fulfill.s(),
    notify.s(),
)
pipeline.apply_async()
```

在 Celery chain 中，每个 task 的返回值作为第一个参数传给下一个 task。要迁移 Celery chain，把链中的每个 task 转换为同一个 Hatchet workflow 中的 task，然后用 parents 表达执行顺序。第一个 task 没有父级，第二个 task 依赖第一个，之后的每个 task 依赖它前面的那个 task。

**Hatchet：**

```python
order_pipeline = hatchet.workflow(name="OrderPipeline", input_validator=OrderInput)


@order_pipeline.task(execution_timeout=timedelta(seconds=30))
async def validate(input: OrderInput, ctx: Context) -> OrderValidated:
    ok = await check_inventory(input.order_id)
    return OrderValidated(order_id=input.order_id, valid=ok)


@order_pipeline.task(parents=[validate])
async def charge(input: OrderInput, ctx: Context) -> ChargeResult:
    parent = ctx.task_output(validate)
    cid = await process_charge(parent.order_id)
    return ChargeResult(order_id=input.order_id, charge_id=cid)


@order_pipeline.task(parents=[charge])
async def fulfill(input: OrderInput, ctx: Context) -> FulfillResult:
    parent = ctx.task_output(charge)
    tracking = await ship_order(parent.order_id)
    return FulfillResult(order_id=input.order_id, tracking_number=tracking)


@order_pipeline.task(parents=[fulfill])
async def notify(input: OrderInput, ctx: Context) -> NotifyResult:
    parent = ctx.task_output(fulfill)
    await send_notification(parent.order_id)
    return NotifyResult(order_id=input.order_id, notified=True)
```

变化点：

- **依赖声明在 task 上**，而不是在调用点。`parents=[validate]` 表示"在 `validate` 完成后运行"。
- **父级输出通过 `ctx.task_output(parent_task)` 显式访问**，而不是作为位置参数传入。
- **workflow 作为整体被触发。** 用 `await order_pipeline.aio_run(OrderInput(...))` 替换 `pipeline.apply_async()`。你不需要把各个 task 调用串起来。

### Celery group 到并行 DAG task

Celery 的 `group` 并行运行多个 task。如果并行 task 在定义 workflow 时已知，可以把它们迁移为具有相同父级（或没有父级、可立即启动）的 Hatchet DAG task。

**Celery：**

```python
from celery import group

checks = group(
    check_inventory.s(order_id),
    check_fraud.s(order_id),
)
checks.apply_async()
```

要迁移这个模式，在同一个 Hatchet workflow 中定义这两个 task，并且不让其中一个依赖另一个。如果 Celery 代码还会等待并合并 group 的结果，那是一个额外的聚合步骤，因此需要添加一个以这些并行 task 为父级的下游汇聚 task。

**Hatchet：**

```python
order_checks = hatchet.workflow(name="OrderChecks", input_validator=OrderInput)


@order_checks.task()
async def check_inventory_task(input: OrderInput, ctx: Context) -> CheckResult:
    ok = await check_inventory(input.order_id)
    return CheckResult(passed=ok)


@order_checks.task()
async def check_fraud(input: OrderInput, ctx: Context) -> CheckResult:
    ok = await run_fraud_check(input.order_id)
    return CheckResult(passed=ok)
```

变化点：

- **并行性移入 workflow 定义。** 相互没有依赖的 task 可以并发运行。
- **调用点启动的是 workflow，而不是 `group(...)`。** 你把 workflow 作为整体触发，而不是动态构建 Canvas group。
- **聚合可能变成汇聚 task。** 如果 Celery 代码等待 group 结果并合并，需要添加一个以并行 task 为父级的下游 task。
- **运行时扇出是另一种模式。** 如果你的 Celery group 是由运行时列表构建的，例如 `group(process.s(item) for item in items)`，请使用[子任务派生](<../06. durable-execution（持久化执行）/02. child-spawning.md>)单独迁移。

### 动态 Celery group 到子任务派生

有些 Celery group 是由只在运行时才能知道的列表构建的：

**Celery：**

```python
from celery import group

items = get_items_for_order(order_id)
result = group(process_item.s(item_id) for item_id in items)()
```

这与已知 task 的静态 group 不同。Hatchet DAG 是预先定义的，因此当子 task 的数量取决于运行时输入时，它并不合适。要迁移这种模式，请使用[子任务派生](<../06. durable-execution（持久化执行）/02. child-spawning.md>)。父 task 接收列表，使用 `aio_run_many` 为每一项派生一个子 run，并收集结果：

```python
@hatchet.task(name="process-item", input_validator=ItemInput)
async def process_item(input: ItemInput, ctx: Context) -> ItemResult:
    result = await do_work(input.item_id)
    return ItemResult(item_id=input.item_id, status=result)


@hatchet.task(name="fan-out-items", input_validator=OrderInput)
async def fan_out_items(input: OrderInput, ctx: Context) -> dict[str, list[ItemResult]]:
    items = await get_items_for_order(input.order_id)

    results = await process_item.aio_run_many(
        [
            process_item.create_bulk_run_item(input=ItemInput(item_id=item_id))
            for item_id in items
        ],
    )

    return {"results": results}
```

变化点：

- **在父 task 内部构建扇出。** 父 task 计算运行时列表并调用 `aio_run_many`，而不是在调用点构造 `group(...)`。
- **每一项变成一个子 run。** 子 task 或 workflow 从运行时列表中接收一项。
- **在派生子任务的地方收集结果。** 用 `aio_run_many` 返回给父 task 的结果替换 `GroupResult` 处理逻辑。

### Celery chord 到 DAG 汇聚

Celery 的 `chord` 并行运行一组 task，然后在组内所有 task 完成后运行一个回调。当并行 task 事先已知时，把这种模式迁移为带多个父级的 Hatchet DAG 汇聚 task。

**Celery：**

```python
from celery import chord

result = chord(
    [fetch_a.s(order_id), fetch_b.s(order_id), fetch_c.s(order_id)]
)(aggregate.s())
```

`aggregate` 回调接收来自 group 的结果列表。要迁移静态 chord，让聚合 task 依赖每个并行 task，并显式读取每个父级的输出。

**Hatchet：**

```python
@workflow.task(parents=[fetch_a, fetch_b, fetch_c])
async def aggregate(input, ctx):
    a = ctx.task_output(fetch_a)
    b = ctx.task_output(fetch_b)
    c = ctx.task_output(fetch_c)
    ...
```

变化点：

- **扇入通过多个父级声明。** 带 `parents=[fetch_a, fetch_b, fetch_c]` 的 task 只有在列出的所有父级完成后才会运行。
- **父级输出逐个访问。** 聚合 task 不是作为回调参数接收 group 结果列表，而是对每个父级调用 `ctx.task_output(parent)`。
- **运行时规模的 chord 需要子任务派生。** 如果你的 Celery chord 由运行时规模的 group 构建，例如 `chord([fetch.s(url) for url in urls])(aggregate.s())`，请用子任务派生和显式的结果收集来迁移，而不是静态的 DAG 汇聚 task。

## 步骤 9：替换 result backend 和 Flower 监控

在 Celery 中，结果获取和任务状态检查依赖已配置的 result backend。如果你的应用调用 `AsyncResult.get()` 或检查 `AsyncResult.state`，请把这些模式迁移到 Hatchet 的返回结果式调用方法、`TaskRunRef` 或 [runs 客户端](<../../reference/30. runs.md>)。

Flower 是一个单独的清理步骤。由于 Hatchet 会在控制台中记录 run 状态、日志、重试尝试、耗时和 workflow 关系，迁移完成后不再需要 Flower 来提供基本的运行时可见性。

考虑下面这段 Celery 代码：它将一个 task 入队、获取结果、保存 task ID 以便稍后查找，并检查任务状态：

**Celery：**

```python
# Wait for the result
async_result = process_image.delay(
    "https://example.com/photo.png",
    ["thumbnail"],
)
output = async_result.get(timeout=10)
print(output["processed_url"])

# Fire-and-forget, then retrieve later
async_result = process_image.apply_async(
    args=["https://example.com/photo.png", ["blur"]],
)
task_id = async_result.id

# Check task state later
state = async_result.state
print(state)  # PENDING, SUCCESS, FAILURE, RETRY, or REVOKED

# Retrieve the result when ready
output = async_result.get(timeout=10)
print(output["processed_url"])
```

> **Info:** 如果你的应用基于 Celery 任务状态做分支，迁移期间请审查这些逻辑，
>   而不是一对一地重命名状态。例如，Celery 只有在配置了
>   `track_started=True` 或 `task_track_started` 时才会报告 `STARTED`。
>   在 Hatchet 中，依赖 `STARTED` 的逻辑通常映射为检查 `RUNNING` run 状态。

把结果处理代码迁移到 Hatchet 时，首先判断调用方是需要立即得到结果，还是只需要一个 run 引用。调用方应等待结果时使用 `.run()` / `.aio_run()`。调用方应入队工作并稍后检查或获取 run 时使用 `wait_for_result=False`。

**Hatchet：**

```python
async def result_handling_example() -> None:
    # Wait for the result directly (replaces AsyncResult.get())
    result = await process_image.aio_run(
        ImageInput(image_url="https://example.com/photo.png", filters=["thumbnail"]),
    )
    print(result.processed_url)

    # Fire-and-forget, then retrieve later (replaces AsyncResult pattern)
    ref = await process_image.aio_run(
        ImageInput(image_url="https://example.com/photo.png", filters=["blur"]),
        wait_for_result=False,
    )
    run_id = ref.workflow_run_id  # available immediately

    # Check run status (replaces AsyncResult.state)
    status = await hatchet.runs.aio_get_status(run_id)
    print(status)  # QUEUED, RUNNING, COMPLETED, FAILED, or CANCELLED

    # Retrieve the result when ready
    result = await ref.aio_result()
    print(result.processed_url)
```

变化点：

- **结果获取默认是直接的。** 调用方应等待 task 结果时，用 `.run()` 或 `.aio_run()` 替换 `AsyncResult.get()`。
- **Fire-and-forget 返回 run 引用。** 调用方应入队工作并继续时使用 `wait_for_result=False`。返回的 `TaskRunRef` 包含 `.workflow_run_id` 和 `.result()` / `.aio_result()`。
- **状态检查移至 runs 客户端。** 应用代码需要 run 状态时，用 `hatchet.runs.aio_get_status(workflow_run_id)` 替换 `AsyncResult.state` 检查。
- **Flower 变为部署清理项。** 一旦迁移后的工作负载不再经过 Celery，移除 Flower 进程，改用 Hatchet 控制台查看 run。

## 步骤 10：迁移其他 Celery 项目面

本节覆盖生产项目中常见、但没有一一对应 Hatchet 等价物的 Celery 特性。对每一项，先确定你的应用所依赖的 Celery 行为，再将其迁移到最接近的 Hatchet 模式。

### 队列与路由

Celery 使用 `task_routes` 和命名队列控制哪些 worker 处理哪些 task：

**Celery：**

```python
# celeryconfig.py
task_routes = {
    "tasks.process_image": {"queue": "image-processing"},
    "tasks.send_email": {"queue": "notifications"},
}
```

```bash
celery -A tasks worker -Q image-processing
```

在 Hatchet 中，路由通过在每个 worker 上注册特定 task 来处理。要迁移你的 Celery 路由，删除该 task 的队列路由，并将迁移后的 Hatchet task 注册到应运行它的 worker 上。

**Hatchet：**

```python
def start_image_worker() -> None:
    """Register only image-processing tasks on this worker."""
    worker = hatchet.worker(
        "image-processing-worker",
        slots=4,
        workflows=[process_image],
    )
    worker.start()
```

变化点：

- **`task_routes` 和绑定队列的 worker 变为 worker 注册。** 用在 `workflows=[...]` 中注册可执行 task 和 workflow 的 Hatchet worker，替换 Celery 的队列路由。
- **高级分配使用 worker 标签。** 如果你需要加权路由或基于能力的分配，Hatchet 支持 [worker affinity](<../07. workers（工作进程）/04. worker-affinity.md>)：task 声明 `desired_worker_labels`，worker 广播自己的能力。这取代了基于 exchange 的路由模式。
- **这是重新设计，而不是重命名。** 简单的 queue-per-worker 路由变为显式的 worker 注册。复杂的路由规则应在迁移期间对照 worker affinity 评估。

### 信号、钩子与进度更新

Celery 为 task 生命周期事件提供[信号](https://docs.celeryq.dev/en/stable/userguide/signals.html)。一个常见的模式是在失败时记录日志或告警。Celery 还支持在运行中的 task 内通过 `self.update_state(state="PROGRESS", meta={...})` 报告进度。

**Celery：**

```python
from celery.signals import task_failure

@task_failure.connect
def handle_task_failure(sender=None, task_id=None, exception=None, **kwargs):
    notify_ops_team(task_id, exception)
```

把 Celery 信号和进度上报迁移到 Hatchet 的 workflow 级钩子和结构化日志。如果信号处理的是 workflow 级的成功或失败，迁移为 workflow 钩子。如果是报告进度，则移入 task 中用 `ctx.log()` 或流式处理：

**Hatchet：**

```python
hook_example = hatchet.workflow(name="HookExample", input_validator=OrderInput)


@hook_example.task()
async def process_order(input: OrderInput, ctx: Context) -> dict[str, str]:
    ctx.log(f"Processing order {input.order_id}")
    await process_charge(input.order_id)
    ctx.log(f"Order {input.order_id} charged")
    return {"status": "charged"}


@hook_example.on_failure_task()
async def on_order_failure(input: OrderInput, ctx: Context) -> None:
    ctx.log(f"Order {input.order_id} failed, notifying support")


@hook_example.on_success_task()
async def on_order_success(input: OrderInput, ctx: Context) -> None:
    ctx.log(f"Order {input.order_id} completed successfully")
```

变化点：

- **`task_failure` / `task_success` 信号变为 workflow 钩子。** `@workflow.on_failure_task()` 在 workflow 中任何 task 失败后运行；`@workflow.on_success_task()` 在所有 task 成功后运行。它们是 workflow 内的 task，而不是全局信号处理器。
- **人类可读的进度移至日志。** 使用 [`ctx.log()`](<../08. observability（可观测性）/01. logging.md>) 发送可在控制台中查看的进度消息。
- **实时进度数据移至流。** 对于应用代码消费的实时进度数据，使用 [`ctx.put_stream()`](<../09. operations（运维）/02. streaming.md>) 向订阅者推送数据。
- **逐个 task 的 `task_prerun` / `task_postrun` 信号没有直接等价物。** 如果你的项目用它们在单个 task 前后做设置或清理，可考虑[依赖注入](<../../reference/21. dependency-injection.md>)。其他横切行为可能需要小幅重新设计。

### 取消

Celery 通过 `AsyncResult` 上的 `revoke()` 取消任务：

**Celery：**

```python
result = process_image.delay("https://example.com/photo.png", ["blur"])
result.revoke()                    # cancel if still pending
result.revoke(terminate=True)      # also terminate if running
```

Hatchet 通过 runs 客户端、控制台或 `CANCEL_IN_PROGRESS` 等并发策略支持[任务取消](<../04. reliability（可靠性）/03. cancellation.md>)。要以编程方式取消 run，使用 `hatchet.runs.cancel(run_id)`。运行中的 task 应通过检查 `ctx.is_cancelled` 来配合取消：

**Hatchet：**

```python
ref = await process_image.aio_run(
    ImageInput(image_url="https://example.com/photo.png", filters=["blur"]),
    wait_for_result=False,
)

# Cancel a run by ID
await hatchet.runs.aio_cancel(ref.workflow_run_id)

# Inside a task: cooperate with cancellation
@hatchet.task()
async def long_running(input, ctx):
    for batch in batches:
        if ctx.is_cancelled:
            return {"status": "cancelled"}
        await process_batch(batch)
    return {"status": "done"}
```

变化点：

- **`result.revoke()` 变为 `hatchet.runs.cancel(...)` / `hatchet.runs.aio_cancel(...)`。** Celery 通过 `AsyncResult` 对象取消；Hatchet 通过 [runs 客户端](<../../reference/30. runs.md>)或控制台，使用 workflow run ID 取消。
- **运行中的 task 必须配合。** Celery 的 `revoke(terminate=True)` 向 worker 进程发送信号。Hatchet 设置一个取消标志，task 通过 `ctx.is_cancelled` 检查。长时间运行的 task 应检查该标志，以便及时停止并执行清理逻辑。
- **并发策略可以自动取消。** Hatchet 的 `CANCEL_IN_PROGRESS` 策略在同一并发键有新 run 到达时取消已有 run。这在 Celery 中没有对应物。

### 优先级

Celery 的优先级在任务入队时指定，数值的含义取决于 broker。

**Celery：**

```python
process_image.apply_async(
    args=["https://example.com/photo.png", ["blur"]],
    priority=9,  # broker-dependent scale
)
```

把对优先级敏感的任务调用迁移到 Hatchet 时，用 Hatchet 的优先级枚举替换 broker 特定的数值优先级。Hatchet 支持[三个优先级级别](<../05. flow-control（流控）/03. priority.md>)：`Priority.LOW`、`Priority.MEDIUM` 和 `Priority.HIGH`。你可以在触发 run 时设置优先级，也可以在 workflow 上定义默认优先级。

**Hatchet：**

```python
from hatchet_sdk import Priority

ref = await process_image.aio_run(
    ImageInput(image_url="https://example.com/photo.png", filters=["blur"]),
    wait_for_result=False,
    priority=Priority.HIGH,
)
```

变化点：

- **broker 特定的数字变为 Hatchet 优先级级别。** 用 `Priority.LOW`、`Priority.MEDIUM` 或 `Priority.HIGH` 替换 Celery 数值优先级。
- **优先级可以按 run 设置，也可以作为 workflow 默认值。** 优先级随调用点变化时使用按 run 优先级；该 workflow 的所有 run 应共享同一优先级时使用 workflow 默认值。
- **优先级作用于同一 workflow 类型。** 同一 workflow 的高优先级 run 会先于低优先级 run 调度。优先级不影响不同 workflow 类型之间的调度。
- **依赖优先级的行为需要验证。** Celery broker 优先级和 Hatchet 调度优先级是不同的模型，请验证依赖精确顺序的 workflow。

### 测试迁移后的 task

Celery 项目有时会在测试中使用 `task_always_eager`，尽管 Celery 自己的文档并不[推荐](https://docs.celeryq.dev/en/stable/userguide/testing.html)在单元测试中这样做：

**Celery：**

```python
task_always_eager = True

result = process_image.delay("https://example.com/photo.png", ["thumbnail"])
assert result.get()["processed_url"] == "https://cdn.example.com/photo.png"
```

Hatchet task 可以在不运行引擎的情况下使用 `.mock_run()`（同步）或 `.aio_mock_run()`（异步）进行单元测试，它们用 mock context 直接执行 task 函数：

**Hatchet：**

```python
async def test_process_image() -> None:
    result = await process_image.aio_mock_run(
        input=ImageInput(
            image_url="https://example.com/photo.png",
            filters=["thumbnail"],
        ),
    )
    assert result.processed_url == "https://cdn.example.com/photo.png"
```

变化点：

- **`task_always_eager` 被 `.mock_run()` / `.aio_mock_run()` 取代。** 它们在本地执行 task 函数而不连接 Hatchet 引擎，类似于直接调用函数，但使用提供 `retry_count`、`additional_metadata` 和 `lifespan` 的 mock context。
- **集成测试使用 `.run()` / `.aio_run()`。** 要针对完整的 Hatchet 引擎测试，在本地或测试实例运行时调用 `.run()` 或 `.aio_run()`。
- **模式示例（包括同步、异步、持久化和 workflow 级 mock 测试）请参见[单元测试示例](https://github.com/hatchet-dev/hatchet/tree/main/sdks/python/examples/unit_testing)**。

## 迁移前需要审查的注意事项

在结束迁移之前，请审查以下需要设计决策（而非机械代码变更）的方面：

- **task 函数签名。** 每个 Hatchet task 接收 `(input, ctx)` 而不是位置参数。为参数签名各异的 task 创建 Pydantic 输入模型通常是最大的机械性工作量。
- **Canvas -> DAG 和子任务派生。** Celery Canvas 组合必须重构为 Hatchet DAG workflow 或子任务派生。这是设计变更，不是重命名。
- **手动重试。** Celery 的 `self.retry()` 没有 Hatchet 等价物。围绕 `NonRetryableException` 重构，或在 task 内部针对特定调用处理重试。
- **生命周期钩子。** `task_prerun`、`task_postrun` 等 Celery 信号在 Hatchet 中需要 workflow 级钩子、依赖注入或重构。
- **队列路由。** Celery 的 `task_routes` 和命名队列变为显式 worker 注册，以及可选的 worker affinity（一种不同的路由模型）。

## 迁移后值得采用的 Hatchet 原生特性

task 在 Hatchet 上运行后，这些特性超越了与 Celery 的对等：

- **[全局速率限制](<../05. flow-control（流控）/02. rate-limits.md>)：** 基于键、在所有 worker 之间统一生效的速率限制。Celery 的 `rate_limit` 仅限单个 worker。
- **[并发策略](<../05. flow-control（流控）/01. concurrency.md>)：** 带有 cancel-in-progress、cancel-newest 等策略的按键并发控制。Celery 没有按 task 的并发控制。
- **[持久化 sleep](<../06. durable-execution（持久化执行）/03. durable-sleep.md>)：** 暂停 workflow 数分钟、数小时或数天而不占用 worker slot。
- **[持久化 event 等待](<../06. durable-execution（持久化执行）/04. durable-event-waits.md>)：** 暂停直到外部 event 到达。适合 webhook 驱动或 human-in-the-loop 工作流。
- **[持久化 task](<../06. durable-execution（持久化执行）/01. durable-tasks.md>)：** 带检查点的命令式工作流组合，适合长时间运行的有状态工作流。

基础迁移不需要其中任何一项。当你的工作负载从后台任务成长为持久化工作流时，它们会变得有用。

基础迁移跑通后，可为 I/O 密集型 task 使用[异步 API](<../../reference/18. asyncio.md>)，用 [lifespan](<../../reference/20. lifespans.md>) 在每个 worker 上只初始化一次共享资源，用[依赖注入](<../../reference/21. dependency-injection.md>)向 task 传递常用依赖而无需在每个函数中手动装配。

## 迁移所有工作负载之前

迁移不必是全有或全无的。如果有以下情况，可考虑把特定工作负载保留在 Celery 上：

- 它们是已经足够可靠、不需要编排或可观测性的简单 fire-and-forget 任务。
- 它们依赖替换成本高昂的 Celery 生态集成（django-celery-beat、django-celery-results 或 broker 特定功能）。
- 它们需要极高的吞吐量，且不需要持久化留存、可观测性或工作流编排。迁移这些工作负载前，请先审阅 Hatchet 的[架构与保障](<../11. evaluating-hatchet（评估）/01. architecture-and-guarantees.md#good-fit-for>)。

## 最终清理

最后一个 Celery task 迁移完成后，从依赖文件中移除 `celery` 包声明（包括所有 Celery extras），并重新生成 lock 文件。`kombu`、`amqp` 等传递依赖会被自动移除。仅在没有其他代码使用 broker 客户端包（如 `redis`）时才删除它们。当没有任何引用时，删除 `celeryconfig.py` 以及 Celery 特定的环境变量（`broker_url`、`result_backend` 等）。从部署配置中移除 Celery worker、Beat 和 Flower 的进程定义。
