# Hatchet Worker 故障排查

本指南覆盖部署和运维 Hatchet worker 时的常见问题。

## 快速调试清单

深入具体问题之前，先过一遍这些检查：

1. **验证 API token** — 确认 `HATCHET_CLIENT_TOKEN` 与 Hatchet dashboard 中为你的 tenant 生成的 token 一致。
2. **检查 worker 日志** — 在 worker 输出中查找连接错误、心跳失败或崩溃堆栈。
3. **检查 dashboard** — 进入 Workers 标签页，查看 worker 是否已注册且健康。
4. **确认网络连通性** — worker 需要通过 gRPC 连到 Hatchet engine。防火墙、VPN 或缺失的 TLS 配置都可能阻断连接。
5. **检查 SDK 版本** — 确保 SDK 版本与 engine 版本兼容。版本不匹配可能导致隐蔽的故障。

## Could not send task to worker

如果在 task 的事件历史中看到这个错误，可能是以下原因：

1. worker 在 task 发送过程中关闭了网络连接。可能是 worker 崩溃或下线。

2. 负载太大，worker 无法接收或 Hatchet engine 无法发送。默认最大负载为 4MB。考虑减小 task 的输入或输出数据。

3. worker 的网络连接上有大量在途 task 积压，正在拒绝新 task。这种情况可能发生在 worker 与 Hatchet engine 地理距离较远，或网络问题导致延迟时。Hatchet Cloud 默认运行在 `us-west-2`（美国俄勒冈），因此建议将 worker 部署在靠近该区域的位置以获得最佳性能。

   如果你是自托管，可以在 Hatchet engine 配置中通过 `SERVER_GRPC_WORKER_STREAM_MAX_BACKLOG_SIZE` 环境变量增大最大积压量。默认值为 20。

## Dashboard 中看不到 worker

如果你已部署 worker 但在 Hatchet dashboard 中看不到，很可能是：

1. API token 无效或错误。确保启动 worker 所用的 token 与 dashboard 中为你的 tenant 生成的 token 一致。

2. worker 心跳没有到达 Hatchet engine。这种情况会在 worker 输出中看到大量报错日志。

## Task 卡在 QUEUED 状态

如果 task 一直停留在 `QUEUED` 状态、从未进入 `RUNNING`：

1. **没有 worker 注册该 task** — 检查 dashboard 的 Workers 标签页，确认有 worker 注册并处理该 task 名称。如果你最近重命名了 task，确保 worker 已用更新的代码重启。

2. **所有 worker slot 已满** — 如果每个 slot 都被其他 task 占用，新 task 会在队列中等待。在 dashboard 中检查 worker 利用率或增大 [slot 数量](<../02. core-concepts（核心概念）/02. workers.md#slots>)。[slot cost](<../07. workers（工作进程）/05. slot-cost.md>) 高于所有 worker slot 数的 task 永远无法被调度，会在调度超时后被取消。

3. **并发或限流阻塞** — 如果你配置了[并发限制](<../05. flow-control（流控）/01. concurrency.md>)或[限流](<../05. flow-control（流控）/02. rate-limits.md>)，task 可能是被有意扣留的。检查你的配置。

## Worker 反复断连

如果你的 worker 反复连接后又掉线：

1. **资源耗尽** — worker 进程可能内存或 CPU 耗尽，被操作系统或编排器杀死（OOM kill）。检查系统日志并提高资源限制。

2. **网络不稳定** — worker 与 engine 之间的间歇性连通问题会导致重连循环。检查 worker 与 engine 之间的丢包率或高延迟。

3. **未配置优雅停机** — 如果部署平台发送 `SIGTERM` 而 worker 没有处理它，在途 task 可能被打断。确保 worker 正确处理停机信号并给 task 留出完成时间。

## Dashboard 中出现幽灵 worker

这通常是因为已部署环境中仍有 worker 在运行。最常见于 worker 终止周期很长的场景，或本地开发环境中 worker 进程泄漏。如果在本地开发环境，通常可以用 `ps -a | grep worker`（或你的入口二进制名称）查看运行中的 Hatchet worker 进程并手动 kill。
