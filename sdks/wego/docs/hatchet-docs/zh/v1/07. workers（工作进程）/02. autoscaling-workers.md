# Worker 自动扩缩容

Hatchet 提供了 Task Stats API，使你能够为 worker 池实现自动扩缩容（autoscaling）。通过查询实时的队列深度和任务分布，你可以基于实际工作负载需求动态地扩缩 worker。

## Task Stats API

Task Stats 端点返回整个 tenant 中排队和运行中任务的当前统计信息，按 task 名称、queue 和并发组进行细分。

### 端点

```
GET /api/v1/tenants/{tenantId}/task-stats
```

### 认证

该端点需要使用有效的 API token 进行 Bearer token 认证：

```
Authorization: Bearer 
```

### 响应格式

响应是一个以 task 名称为键的 JSON 对象，每个 task 包含排队中和运行中两种状态的统计信息：

```json
{
  "my-task": {
    "queued": {
      "total": 150,
      "queues": {
        "my-task:default": 100,
        "my-task:priority": 50
      },
      "concurrency": [
        {
          "expression": "input.user_id",
          "type": "GROUP_ROUND_ROBIN",
          "keys": {
            "user-123": 10,
            "user-456": 15
          }
        }
      ],
      "oldest": "2024-01-15T10:30:00Z"
    },
    "running": {
      "total": 25,
      "oldest": "2024-01-15T10:25:00Z",
      "concurrency": []
    }
  }
}
```

每个 task 统计包含：

- **total**：该状态下 task 的总数
- **concurrency**：在各并发组中的分布（如果配置了并发限制）
- **oldest**：该状态下最早 task 的时间戳

以下字段仅对 `queued` 状态的 task 提供：

- **queues**：按 queue 名称细分的 task 数量

### 使用示例

```bash
curl -H "Authorization: Bearer your-api-token-here" \
  https://cloud.onhatchet.run/api/v1/tenants/707d0855-80ab-4e1f-a156-f1c4546cbf52/task-stats
```

## 使用 KEDA 自动扩缩容

[KEDA](https://keda.sh)（Kubernetes Event-driven Autoscaling）可以利用 Task Stats API，基于队列深度自动扩缩你的 worker 部署。

### 配置 KEDA ScaledObject

创建一个查询 Hatchet Task Stats API 并根据排队 task 数量扩缩 worker 部署的 `ScaledObject`：

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: hatchet-worker-scaler
spec:
  scaleTargetRef:
    name: hatchet-worker
  minReplicaCount: 1
  maxReplicaCount: 10
  triggers:
    - type: metrics-api
      metadata:
        targetValue: "100"
        url: "https://cloud.onhatchet.run/api/v1/tenants/YOUR_TENANT_ID/task-stats?taskNames=my-task"
        valueLocation: "my-task.queued.total"
        authMode: "bearer"
      authenticationRef:
        name: hatchet-api-token
---
apiVersion: v1
kind: Secret
metadata:
  name: hatchet-api-token
type: Opaque
stringData:
  token: "your-api-token-here"
---
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: hatchet-api-token
spec:
  secretTargetRef:
    - parameter: token
      name: hatchet-api-token
      key: token
```

> **Info:** `valueLocation` 字段使用 JSONPath 风格的表示法从响应中提取特定值。
>   请将 `my-task` 调整为你实际的 task 名称。
>
> 请通过 `taskNames` 查询参数传入每一个你要据其扩缩的 task，这样端点才能保证
> 在没有排队工作时 JSONPath 解析结果为 `0`。如果不传，响应可能是 `{}`，
> KEDA 的 metrics-api scaler 将无法从零开始扩容。

### 基于多个 task 扩缩容

如果同一个 worker 处理多种 task 类型，你可以创建多个触发器，或使用聚合了总数的自定义 metrics 端点：

```yaml
triggers:
  - type: metrics-api
    metadata:
      targetValue: "50"
      url: "https://cloud.onhatchet.run/api/v1/tenants/YOUR_TENANT_ID/task-stats?taskNames=task-a"
      valueLocation: "task-a.queued.total"
      authMode: "bearer"
    authenticationRef:
      name: hatchet-api-token
  - type: metrics-api
    metadata:
      targetValue: "50"
      url: "https://cloud.onhatchet.run/api/v1/tenants/YOUR_TENANT_ID/task-stats?taskNames=task-b"
      valueLocation: "task-b.queued.total"
      authMode: "bearer"
    authenticationRef:
      name: hatchet-api-token
```

### 基于 worker slot 利用率扩缩容

除了基于队列深度，你还可以基于 worker slot 的利用率来扩缩容。Hatchet 暴露了 [Prometheus 指标](/self-hosting/prometheus-metrics)，按唯一的 worker 标签 `(key, value)` 对和 slot 类型跟踪已用 slot 和总 slot 数，因此每个带标签的 worker 池都可以独立扩缩：

- `hatchet_tenant_worker_label_slots{tenant_id, label_key, label_value, slot_type}`：带有该标签对的所有 worker 中该 slot 类型的总 slot 数
- `hatchet_tenant_used_worker_label_slots{tenant_id, label_key, label_value, slot_type}`：带有该标签对的所有 worker 中该 slot 类型的已用 slot 数

`slot_type` 标签区分了 worker 相互独立的 slot 池（例如 `default` 和 `durable`）。请根据你的 task 实际消耗的 slot 类型（通常是 `default`）进行扩缩，避免一个庞大但基本空闲的 durable slot 池掩盖了 default slot 的饱和状况。

在时间窗口内分别对已用和总 slot 的 gauge 求平均，再相除，即可得到该窗口内 worker 池的平均利用率：

```promql
avg_over_time(hatchet_tenant_used_worker_label_slots{tenant_id="<tenant-id>", label_key="pool", label_value="gpu", slot_type="default"}[5m])
/
avg_over_time(hatchet_tenant_worker_label_slots{tenant_id="<tenant-id>", label_key="pool", label_value="gpu", slot_type="default"}[5m])
```

该查询返回 0 到 1 之间的值。分别对分子和分母求平均（而不是对比率求平均），可以保证在窗口内 worker 扩容或缩容时结果依然正确。

借助 [KEDA 的 Prometheus scaler](https://keda.sh/docs/latest/scalers/prometheus/)，当平均利用率超过 75% 时你可以扩容 worker 部署：

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: gpu-worker-scaler
spec:
  scaleTargetRef:
    name: gpu-worker
  minReplicaCount: 1
  maxReplicaCount: 10
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        threshold: "0.75"
        query: |
          avg_over_time(hatchet_tenant_used_worker_label_slots{tenant_id="<tenant-id>", label_key="pool", label_value="gpu", slot_type="default"}[5m])
          /
          avg_over_time(hatchet_tenant_worker_label_slots{tenant_id="<tenant-id>", label_key="pool", label_value="gpu", slot_type="default"}[5m])
```

未携带目标标签的 worker 不会影响查询结果。若要对某个 tenant 的整个 worker 集群扩缩容（不考虑标签），请改用按 worker 统计的 gauge：

```promql
sum by (tenant_id) (avg_over_time(hatchet_tenant_used_worker_slots{tenant_id="<tenant-id>"}[5m]))
/
sum by (tenant_id) (avg_over_time(hatchet_tenant_worker_slots{tenant_id="<tenant-id>"}[5m]))
```

### 按元数据标签基于队列积压扩缩容

如果希望通过 Prometheus 而非 Task Stats API 基于队列深度扩缩容，Hatchet 暴露了队列大小的 gauge，其中包括一个按排队 task 的附加元数据 `(key, value)` 对分组的 gauge。只有带 `prom_` 前缀的元数据键会被导出。如果你的 GPU 工作负载为 workflow run 打了附加元数据标签（例如 `prom_pool: gpu`），GPU 积压就可以驱动它自己的 scaler：

```promql
sum(hatchet_tenant_additional_metadata_queue_size{tenant_id="<tenant-id>", key="prom_pool", value="gpu"}) or vector(0)
```

`or vector(0)` 对缩容到零很重要：一旦队列清空，其时间序列在报告为零后不久就会被移除。还有 `hatchet_tenant_queue_size{tenant_id, queue, workflow_name}` 可用于按特定 queue 或 workflow 的积压进行扩缩。这两个 gauge 都每 15 秒从数据库轮询一次。
