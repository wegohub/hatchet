# 常见问题（FAQ）

本页回答我们最常被问到的一些问题，帮助你更好地使用 Hatchet！

## 如何为 worker 设置多少个 slot？

Hatchet 中 worker 的默认 slot 数是 100。很多情况下，保持默认值完全没问题，尤其是在刚开始使用 Hatchet 时。

随着时间推移，你很可能会遇到两类问题之一：资源枯竭（即 worker 消耗了过多的内存、CPU 等），或者希望从 worker 中榨取更多性能。

如果你的 worker 资源枯竭，基本上有两种选择：

1. 降低 slot 数，让 worker 并发运行更少的工作。这是一种比较粗放的手段，因为它无法让你根据 worker 上工作负载的需求_精细调校_资源。例如，如果你用满了 100% 的内存但只用了 10% 的 CPU，降低 slot 数可能有助于 worker 保持在线，但 CPU 会被严重低效利用。此时你可以：
2. 重新配置 worker 所在机器的规格。例如在上面的例子中，你可以从 CPU 优化型机器迁移到内存优化型机器，从而全面提升资源利用效率。

如果只是部分 task 较重，[task slot cost](<../07. workers（工作进程）/05. slot-cost.md>) 可以让这些 task 消耗多个 slot，这样 slot 数就可以继续按轻型 task 调优。

另一方面，如果你的 worker 资源利用不足，你可以：

1. 增加 slot 数，让它们可以领取更多工作。这对重 I/O 型的 task 尤其有帮助，因为这类 task 大部分时间都在等待。
2. 与资源枯竭的情况类似，你可以下调 worker 所在机器的资源规格。

> **Info:** 一般而言，我们建议单个 worker 的 slot 数不要超过 250-300 太多。
>   到这个程度，进行更多的水平扩展通常更合理。

## 为什么会出现心跳丢失和 task 重新分配？

Hatchet 使用心跳（heartbeat）监控 worker 健康状况。worker 每 **4 秒**发送一次心跳。如果 engine 在 **30 秒**内没有收到心跳，就会认为该 worker 已失活，并将其在途 task 重新入队供其他 worker 领取。

worker 丢失心跳的常见原因有：

- **进程崩溃** - worker 进程意外退出（OOM kill、未处理的异常、SIGKILL）。
- **网络中断** - worker 与 Hatchet engine 之间的连接中断（DNS 故障、防火墙变更、云网络抖动）。
- **资源压力** - 高 CPU 或内存使用可能使 worker 资源匮乏
