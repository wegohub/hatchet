# Hatchet Task 中的并发控制

Hatchet 提供了强大的并发控制功能，帮助你管理 task 的执行。当你的 task 可能被频繁触发或包含长时间运行的步骤，而你希望限制并发执行的数量以防止系统过载、保证公平性或避免竞态条件时，并发控制尤其有用。并发策略既可以添加到 task 上，也可以添加到 workflow 上。

> **Info:** 本页会频繁讨论并发**键**（key）。键是你为 task 或 workflow 提供的
>   [CEL 表达式](<06. cel-expressions.md>)的求值结果。你创建的 CEL 表达式可以引用
>   workflow 的 `input` 和 `additional_metadata`。
>
> 例如，假设 workflow run 以输入 `{"user_id": "abc"}` 和附加元数据 `{"foobar": "bazqux"}` 触发，那么表达式 `input.user_id + ':' + additional_metadata.foobar` 的求值结果为 `abc:bazqux`。

## 为什么使用并发控制？

当你需要确保应用的各用户、项目或组织之间公平地访问资源时，就应当主要使用并发控制。通过限制某个用户在途 task 的数量，可以防止该用户独占系统。


如果你使用静态的 CEL 表达式（如 `'global'`），并发控制还可以全局限制一个 workflow 的运行数量。这种做法和[速率限制](<02. rate-limits.md>)是为每个 workflow 设置吞吐上限的推荐机制。

> **Info:** 并发限制的是同时进行的 run 数量。如果你想控制的是单个 run 消耗的
>   worker 容量——让重型 task 占用比轻型 task 更多的 slot——请参阅
>   [Task Slot Cost](<../07. workers（工作进程）/05. slot-cost.md>)。

## 可用策略：

- [**Group Round Robin（分组轮询）**](#group-round-robin) 将传入的 task 和 workflow run 排队，只在有空闲 slot 打开时才把它们分发给 worker 并触发执行。
- [**Cancel In Progress（取消进行中的运行）**](#cancel-in-progress) 取消与并发键匹配的、正在进行的 task 或 workflow 实例，为新触发的 task 或 workflow run 腾出 slot。
- [**Cancel Newest（取消最新）**](#cancel-newest) 当某个键处于运行状态的 run 数量达到给定限制时，取消该键的所有新传入 task 或 workflow run。
- [**Cancel Queued Except Newest（取消排队任务但保留最新）**](#cancel-queued-except-newest) 当某个键达到给定限制时，取消该键的所有新传入 task 或 workflow run，但最近入队的除外。
- [**Cancel Queued Except Oldest（取消排队任务但保留最早）**](#cancel-queued-except-oldest) 当某个键达到给定限制时，取消该键的所有新传入 task 或 workflow run，但最早入队的除外。

## Group Round Robin

当新的 task 实例被触发时，Group Round Robin 策略会：

1. 根据 task 或 workflow 并发配置中定义的 [CEL 表达式](<06. cel-expressions.md>)确定该 run 所属的键。
2. 根据并发配置允许的最大并发 run 数，检查该并发键是否有空闲 slot。
3. 如果有空闲 slot，新的 task 或 workflow 立即开始执行。
4. 如果没有空闲 slot，新的 task 或 workflow 被加入其键对应的队列。
5. 当一个正在运行的 task 实例完成、该组有空闲 slot 时，按轮询（round-robin）顺序取出该组下一个排队的实例并开始执行。

Group round robin 确保不同组的 task 实例得到公平处理，防止任何单个组独占可用资源。它还有助于降低每个组内实例的延迟，因为它们以轮询方式被处理，而不是严格按触发顺序。Group round robin 还可以用作全局并发控制，限制单个 task 或 workflow 在任意时刻的最大运行数，而不考虑任何分组。你可以将并发键设为常量表达式（如 `'*'`）来启用这种全局并发控制行为。


要使用该策略，请设置 `GROUP_ROUND_ROBIN` 限制策略，并配合 `max_runs` 限制和一个键表达式：

#### Python

```python
class WorkflowInput(BaseModel):
    group: str


concurrency_limit_rr_workflow = hatchet.workflow(
    name="ConcurrencyDemoWorkflowRR",
    concurrency=ConcurrencyExpression(
        expression="input.group",
        max_runs=1,
        limit_strategy=ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
    ),
    input_validator=WorkflowInput,
)
```

#### Typescript

```typescript
export const simpleConcurrency = hatchet.workflow({
  name: 'simple-concurrency',
  concurrency: {
    maxRuns: 1,
    limitStrategy: ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
    expression: 'input.GroupKey',
  },
});
```

#### Go

```go
var maxRuns int32 = 1
strategy := hatchet.GroupRoundRobin

return client.NewStandaloneTask("simple-concurrency",
	func(ctx hatchet.Context, input ConcurrencyInput) (*TransformedOutput, error) {
		// Random sleep between 200ms and 1000ms
		time.Sleep(time.Duration(200+rand.Intn(800)) * time.Millisecond)

		return &TransformedOutput{
			TransformedMessage: input.Message,
		}, nil
	},
	hatchet.WithWorkflowConcurrency(hatchet.Concurrency{
		Expression:    "input.GroupKey",
		MaxRuns:       &maxRuns,
		LimitStrategy: &strategy,
	}),
)
```

#### Ruby

```ruby
CONCURRENCY_LIMIT_RR_WORKFLOW = HATCHET.workflow(
  name: "ConcurrencyDemoWorkflowRR",
  concurrency: Hatchet::ConcurrencyExpression.new(
    expression: "input.group",
    max_runs: 1,
    limit_strategy: :group_round_robin
  )
)

CONCURRENCY_LIMIT_RR_WORKFLOW.task(:step1) do |input, ctx|
  puts "starting step1"
  sleep 2
  puts "finished step1"
end
```

## Cancel In Progress

当新的 task 实例被触发时，Cancel In Progress 策略会：

1. 根据 task 或 workflow 并发配置中定义的 [CEL 表达式](<06. cel-expressions.md>)确定该 run 所属的键。
2. 根据并发配置允许的最大并发 run 数，检查该并发键是否有空闲 slot。
3. 如果有空闲 slot，新的 task 或 workflow 立即开始执行。
4. 如果没有空闲 slot，将取消一个具有相同并发键的、正在运行的 task 或 workflow 实例以腾出 slot，然后新实例立即开始执行。

Cancel In Progress 确保最近触发的 run 始终优先于较早的 run，这在较新输入取代较旧输入、进行中的工作一旦有新 run 到达就变得过时或无关时非常有用。它特别适合只有最新输入才重要的面向用户交互的场景（如聊天消息、表单提交、边输入边搜索）、放弃旧 run 比等待其完成更高效的资源密集型 task，以及任何希望优先处理最新数据或事件而非旧数据的场景。

要使用该策略，请设置 `CANCEL_IN_PROGRESS` 限制策略，并配合 `max_runs` 限制和一个键表达式：

#### Python

```python

        expression="input.group",

    input_validator=WorkflowInput,
```


## Cancel Newest

当新的 task 实例被触发时，Cancel Newest 策略会：

1. 根据 task 或 workflow 并发配置中定义的 [CEL 表达式](<06. cel-expressions.md>)确定该 run 所属的键。
2. 根据并发配置允许的最大并发 run 数，检查该并发键是否有空闲 slot。
3. 如果有空闲 slot，新的 task 或 workflow 立即开始执行。
4. 如果没有空闲 slot，新触发的 run 会立即被取消，让进行中的 run 不受干扰地继续执行。

Cancel Newest 与 Cancel In Progress 恰好相反：它不是为新到来的 run 抢占正在运行的工作，而是保护进行中的 run 不被打扰，让它们在同一个键的任何新工作开始之前完成。这在以下场景很有用：你希望保证长时间运行的 task 实例不受干扰地完成、重启工作的成本超过了处理较新输入的价值，或者你想通过直接拒绝多余的 run（而不是排队）来防止单个组的实例独占可用 slot。

要使用该策略，请设置 `CANCEL_NEWEST` 限制策略，并配合 `max_runs` 限制和一个键表达式：

## Cancel Queued Except Newest

当新的 task 实例被触发时，Cancel Queued Except Newest 策略会：

1. 根据 task 或 workflow 并发配置中定义的 [CEL 表达式](<06. cel-expressions.md>)确定该 run 所属的键。
2. 根据并发配置允许的最大并发 run 数，检查该并发键是否有空闲 slot。
3. 如果有空闲 slot，新的 task 或 workflow 立即开始执行。
4. 如果没有空闲 slot，新触发的 run 会立即被取消，_但最近 `max_runs` 个 task 除外_，它们会保持在排队状态，直到有可用的 slot 容量。

Cancel Queued Except Newest 与 Cancel Newest 非常相似，区别在于它会保留最近入队的 `max_runs` 个 task，直到进行中的 task 运行结束。届时，它会将本来会被取消的最近 `max_runs` 个 task 入队执行。这适用于你希望进行中的 task 阻塞新 task、但仍保证有一个收尾 run 的场景。

举一个更具体的例子，考虑三个 task A、B、C 且 `max_runs=1` 的场景：

- Task A 立即开始执行。
- Task B 保持在排队状态，等待 A 完成，或有另一个 task 入队。
- Task C 作为最新的 task，会在排队状态中取代 Task B，导致 Task B 被取消。
- Task A 执行完成——Task C 在排队状态中等待，并将在 A 完成后立即开始运行。

要使用该策略，请设置 `CANCEL_QUEUED_EXCEPT_NEWEST` 限制策略，并配合 `max_runs` 限制和一个键表达式：

```python
        limit_strategy=ConcurrencyLimitStrategy.CANCEL_QUEUED_EXCEPT_NEWEST,
```

## Cancel Queued Except Oldest

当新的 task 实例被触发时，Cancel Queued Except Oldest 策略会：

1. 根据 task 或 workflow 并发配置中定义的 [CEL 表达式](<06. cel-expressions.md>)确定该 run 所属的键。
2. 根据并发配置允许的最大并发 run 数，检查该并发键是否有空闲 slot。
3. 如果有空闲 slot，新的 task 或 workflow 立即开始执行。
4. 如果没有空闲 slot，新触发的 run 会立即被取消，_但仍处于排队状态的最早 `max_runs` 个 task 除外_，它们会保持在排队状态，直到有可用的 slot 容量。

Cancel Queued Except Oldest 与 Cancel Queued Except Newest 恰好相反：它不是保留最近入队的 task，而是取消较新的 task，保留最早的 `max_runs` 个 task，直到进行中的 task 运行结束。届时，它会将本来会被取消的最早 `max_runs` 个 task 入队执行。这适用于你希望保证某个键等待最久的 run 最终能够执行、同时仍允许最初的 task 完成的场景。

举一个更具体的例子，考虑三个 task A、B、C 且 `max_runs=1` 的场景：

- Task A 立即开始执行。
- Task B 保持在排队状态，等待 A 完成，或有另一个 task 入队。
- Task C 作为两个排队 task 中较新的一个，会立即被取消，Task B 保持在排队状态。
- Task A 执行完成——Task B 在排队状态中等待，并将在 A 完成后立即开始运行。

## 多重并发策略

你还可以组合多个并发策略，构建更复杂的并发控制系统。例如，你可以用一个组键表示特定团队，用另一个组表示该团队中的特定资源，从而更精细地控制 task 的执行速率。

#### Python

```python
class WorkflowInput(BaseModel):
    name: str
    digit: str


concurrency_workflow_level_workflow = hatchet.workflow(
    name="ConcurrencyWorkflowLevel",
    input_validator=WorkflowInput,
    concurrency=[
        ConcurrencyExpression(
            expression="input.digit",
            max_runs=DIGIT_MAX_RUNS,
            limit_strategy=ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
        ),
        ConcurrencyExpression(
            expression="input.name",
            max_runs=NAME_MAX_RUNS,
            limit_strategy=ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
        ),
    ],
)
```

#### Typescript

```typescript
export const multipleConcurrencyKeys = hatchet.workflow({
  name: 'simple-concurrency',
  concurrency: [
    {
      maxRuns: 1,
      limitStrategy: ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
      expression: 'input.Tier',
    },
    {
      maxRuns: 1,
      limitStrategy: ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
      expression: 'input.Account',
    },
  ],
});
```

#### Go

```go
strategy := hatchet.GroupRoundRobin
var maxRuns int32 = 20

return client.NewStandaloneTask("multi-concurrency",
	func(ctx hatchet.Context, input ConcurrencyInput) (*TransformedOutput, error) {
		// Random sleep between 200ms and 1000ms
		time.Sleep(time.Duration(200+rand.Intn(800)) * time.Millisecond)

		return &TransformedOutput{
			TransformedMessage: input.Message,
		}, nil
	},
	hatchet.WithWorkflowConcurrency(
		hatchet.Concurrency{
			Expression:    "input.Tier",
			MaxRuns:       &maxRuns,
			LimitStrategy: &strategy,
		}, hatchet.Concurrency{
			Expression:    "input.Account",
			MaxRuns:       &maxRuns,
			LimitStrategy: &strategy,
		},
	),
)
```

#### Ruby

```ruby

  name: "ConcurrencyWorkflowLevel",
  concurrency: [
    Hatchet::ConcurrencyExpression.new(
      expression: "input.digit",

CONCURRENCY_WORKFLOW_LEVEL_WORKFLOW.task(:task_2) do |input, ctx|
  sleep SLEEP_TIME_WL

```

## 跨 workflow 共享并发

> **Info:** 共享并发策略要求 engine 版本 0.106.0 或更高。

上述所有策略都作用于单个 workflow，但你也可以在多个 workflow 之间共享并发策略。共享通过策略名称实现：所有 workflow 中声明了相同名称的每个 task 都消耗同一个并发限制。

#### Python

```python
# A tenant-scoped strategy is shared across workflows: every task declaring the same name
# consumes the same concurrency limit. The definition rides on workflow registration and
# re-registering the name updates it in place.
shared_limit = ConcurrencyExpression(
    expression="input.group",
    max_runs=1,
    limit_strategy=ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
    name="example-shared-limit",
    is_tenant_scoped=True,
)


@hatchet.task(input_validator=WorkflowInput, concurrency=[shared_limit])
def task_a(input: WorkflowInput, ctx: Context) -> RunWindow:
    return run_window(1.5)


@hatchet.task(input_validator=WorkflowInput, concurrency=[shared_limit])
def task_b(input: WorkflowInput, ctx: Context) -> RunWindow:
    return run_window(1.5)
```

#### Typescript

```typescript
// A tenant-scoped strategy is shared across workflows: every task declaring the same name
// consumes the same concurrency limit. The definition rides on workflow registration and
// re-registering the name updates it in place.
export const sharedLimit: Concurrency = {
  name: 'ts-example-shared-limit',
  isTenantScoped: true,
  expression: 'input.group',
  maxRuns: 1,
  limitStrategy: ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
};

const runWindowTask = async (): Promise => {
  const startMs = Date.now();
  await sleep(SLEEP_TIME_MS);
  return { startMs, endMs: Date.now() };
};

export const concurrencySharedWorkflowA = hatchet.workflow({
  name: 'concurrency-shared-a',
});

concurrencySharedWorkflowA.task({
  name: 'shared-task',
  concurrency: [sharedLimit],
  fn: runWindowTask,
});

export const concurrencySharedWorkflowB = hatchet.workflow({
  name: 'concurrency-shared-b',
});

concurrencySharedWorkflowB.task({
  name: 'shared-task',
  concurrency: [sharedLimit],
  fn: runWindowTask,
});
```

如果你修改了共享并发策略，在下一次 worker 部署和 workflow 重新注册时它会就地更新。

共享策略可以与同一 task 上的内联（workflow 范围）条目自由混用：在并发列表中的位置即链式顺序，因此共享条目可以排在内联条目之前或之后，链中的每个限制都会同时生效。

> **Warning:** 当多个 workflow 链接相同的共享策略时，它们必须彼此一致地排列这些
>   共享策略的顺序。如果不同的注册对相同共享策略的链式顺序不一致，将被拒绝，
>   因为不一致的顺序可能使持有某个共享 slot 同时又在等待另一个 slot 的 run 死锁。

## 使用 max runs 表达式实现动态限制

> **Info:** Max runs 表达式要求 engine 版本 0.106.0 或更高。

并发策略上的 `max_runs` 限制通常是一个固定数字，对所有键生效。你也可以用基于 task 输入的 CEL 表达式按键计算限制，让不同的组从单个策略获得不同的限制。例如，假设你希望应用中不同的定价档位对应不同的限制：可以使用 `max_runs` 表达式定义类似 `input.tier == 'premium' ? 10 : 1` 的内容。

#### Python

```python
# max_runs accepts an int or a CEL expression string. With an expression, each
# concurrency group's limit is computed from the task's input.
@hatchet.task(
    input_validator=WorkflowInput,
    concurrency=[
        ConcurrencyExpression(
            expression="input.account",
            max_runs="input.tier == 'premium' ? 10 : 1",
            limit_strategy=ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN,
        ),
    ],
)
def dynamic_task(input: WorkflowInput, ctx: Context) -> None:
    print("running for account", input.account)
```

#### Typescript

```typescript

```

#### Go


#### Ruby


如果表达式求值失败，将导致 task 失败，并把求值错误作为 task 的失败信息。

如果你修改了表达式，新的限制会在下一次触发的 task 上生效。这不适用于已有 task 的重放：task 必须是新 task。如果限制被调低，`GROUP_ROUND_ROBIN` 策略和 cancel-queued 系列策略会让正在运行的工作完成并停止补充，直到该组降到新限制以下，而 `CANCEL_IN_PROGRESS` 会取消超出新限制的正在运行的工作。
