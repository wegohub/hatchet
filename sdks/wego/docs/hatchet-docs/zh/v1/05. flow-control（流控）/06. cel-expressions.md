# CEL 表达式


[CEL（Common Expression Language）](https://cel.dev/) 是一种小巧的非图灵完备表达式语言，专为快速、安全的求值而设计。Hatchet 在任何需要在触发时根据 run 输入计算值或做出匹配决策的功能中都使用 CEL：并发键、速率限制键、幂等键、批量键、event 过滤器、task 条件以及 webhook 路由。表达式在 Hatchet 引擎上求值，而不是在你的 worker 中，因此它们可以在 task 被分配之前运行。关于这门语言本身的入门介绍，请参阅 [CEL by example](https://celbyexample.com/)。

## Hatchet 接受 CEL 的场景

功能， 表达式的产出， 指南

| 并发键（Concurrency keys） | 一个字符串分组键 | [并发控制](<01. concurrency.md>) |
| --- | --- | --- |
| 动态最大运行数（Dynamic max runs） | 每个并发组的正整数限制 | [并发控制](<01. concurrency.md>) |
| 动态速率限制（Dynamic rate limits） | 一个字符串键；units 和 limit 也可以是整数表达式 | [速率限制](<02. rate-limits.md#dynamic-rate-limits>) |
| 幂等键（Idempotency keys） | 一个字符串键 | [幂等性](<04. idempotency.md>) |
| 批量键（Batch keys） | 一个字符串分区键 | [批量任务](<05. batch-tasks.md#batch-keys>) |
| Event 过滤器（Event filters） | 一个布尔值（是否触发 run） | [事件](<../03. triggers（触发）/04. events.md#event-filters>) |
| 父级条件（`skip_if`、`cancel_if`、`wait_for`） | 一个布尔值 | [DAG](<../06. durable-execution（持久化执行）/06. directed-acyclic-graphs.md#branching-with-parent-conditions>) |
| 用户 event 条件与持久化 event 等待 | 一个布尔值（是否接受该 event） | [持久化事件等待](<../06. durable-execution（持久化执行）/04. durable-event-waits.md#matching-cel-expressions>) |
| 传入 webhook 的 event key 与 scope | 一个字符串 | [Webhooks](<../03. triggers（触发）/05. webhooks.md#event-key-expression>) |

每种上下文暴露的变量集合各不相同，详见下文。引用上下文中不存在的变量会导致表达式失败。失败的并发键、最大运行数、速率限制或批量键表达式会使 run 以失败状态创建，并把求值错误作为失败原因。失败的幂等键表达式会完全跳过该 run，失败的过滤器表达式则意味着过滤器不匹配，因此 run 不会被触发。

## 键表达式：并发、速率限制与批量键

并发键表达式、动态最大运行数表达式、动态速率限制表达式和批量键表达式都在 run 被触发时求值，可用的变量相同：

| 变量 | 含义 |
| --- | --- |
| `input` | 被触发 run 的输入对象 |
| `additional_metadata` | 设置在 run 上的[附加元数据](<../08. observability（可观测性）/05. additional-metadata.md>) |
| `workflow_run_id` | 被触发 run 的 ID，以字符串表示 |
| `parents` | 已完成父 task 的输出，以父 task 的可读 ID 为键（速率限制和批量键可用） |

并发键、批量键和速率限制键必须求值为字符串。动态速率限制的 `units` 和 `limit` 表达式必须求值为整数，动态最大运行数表达式必须求值为正整数，该值会成为该 run 所属组的并发限制。

```text
'customer:' + input.customer_id
```

DAG 中 task 级别的速率限制和批量键表达式可以从父 task 的输出派生键，例如 `'tenant:' + string(parents["lookup"]["tenant_id"])`。并发键和动态最大运行数表达式不能引用 `parents`，否则在注册时会被拒绝。

## 幂等键表达式

幂等键表达式在 run 创建之前求值，因此没有 run ID 可用。引用 `workflow_run_id` 的表达式会在 workflow 注册时被拒绝：

变量， 含义

`input`， 被触发 run 的输入对象
`additional_metadata`， 设置在 run 上的[附加元数据](<../08. observability（可观测性）/05. additional-metadata.md>)

表达式必须求值为字符串。以保留前缀 `hatchet_internal_` 开头的键会被拒绝。

```text
checksum(input.order_id + ':' + input.customer_id)
```

## Event 过滤器表达式

[Event 过滤器](<../03. triggers（触发）/04. events.md#event-filters>)表达式决定一个传入 event 是否触发 workflow。它们必须求值为布尔值：

| 变量 | 含义 |
| --- | --- |
| `input` | 传入 event 的 payload |
| `payload` | 创建过滤器时存储在过滤器上的 payload |
| `additional_metadata` | 随 event 发送的附加元数据 |
| `event_key` | event 的 key，例如 `user:created`，以字符串表示 |
| `event_id` | event 的 ID，以字符串表示 |

```text
input.status == 'active' && input.customer_id == payload.customer_id
```

## Task 条件表达式

[父级条件](<../06. durable-execution（持久化执行）/06. directed-acyclic-graphs.md#branching-with-parent-conditions>)（父 task 上的 `skip_if`、`cancel_if` 和 `wait_for` 条件）针对父 task 的输出求值，必须求值为布尔值：

变量， 含义

`output`， 父 task 的输出对象

```text
output.random_number > 50
```

用户 event 条件（用于 `wait_for` 条件和[持久化 event 等待](<../06. durable-execution（持久化执行）/04. durable-event-waits.md#matching-cel-expressions>)）针对传入 event 的 payload 求值，同样必须求值为布尔值：

变量， 含义

`input`， 传入 event 的 payload

```text
input.user_id == 1234
```

## 传入 webhook 表达式

传入 webhook 上的 [event key 表达式](<../03. triggers（触发）/05. webhooks.md#event-key-expression>)和 [scope 表达式](<../03. triggers（触发）/05. webhooks.md#scope-expression-optional>)针对 webhook 请求求值。两者都必须求值为字符串：

变量， 含义

`input`， webhook 的 JSON body；如果配置了静态 payload，则会与其合并
`headers`， 请求头，以小写 header 名到值的 map 表示

```text
'github:' + headers['x-github-event'] + ':' + input.action
```

## 函数

所有上下文都支持 [CEL 标准库](https://github.com/google/cel-spec/blob/master/doc/langdef.md#standard-definitions)，包括用于检查字段是否存在的 `has()` 等宏：

```text
has(input.custom.value) ? input.custom.value : 'default'
```

除 task 条件表达式外，其余所有上下文还支持 Hatchet 提供的 `checksum` 函数，它返回字符串的 SHA-256 十六进制摘要。当底层值很长时，这有助于保持键简短且统一：

```text
checksum(input.long_document_id)
```

这些上下文（键表达式、event 过滤器和传入 webhook 表达式）还支持 [strings 扩展](https://github.com/google/cel-go/tree/master/ext#strings)，它增加了 `lowerAscii`、`replace`、`split` 等函数。

## 调试表达式

## 定位求值失败

求值失败落在哪里取决于上下文：

上下文， 对 run 的影响， 错误在哪里可见

| 并发、速率限制和批量键 | run 以失败状态创建 | run 的错误信息 |
| --- | --- | --- |
| 幂等键 | 不创建 run | 仅引擎内部（目前不可查询） |
| Event 过滤器 | 过滤器不匹配，不产生 run | 仅引擎内部（目前不可查询） |
| Webhook event key 和 scope 表达式 | 请求被拒绝 | 返回给发送方的 HTTP 400 响应 |

键表达式的失败最容易发现，因为它们会产生一个可见的失败 run。求值错误（包括表达式文本）会成为该 run 的错误信息。你可以在控制台的 run 详情页、REST API 返回的 run 详情中看到它，也可以通过 CLI 的 `hatchet runs get <run-id> -o json` 查看（该错误还会出现在 run 的失败 event 中，可通过 `hatchet runs events <run-id>` 查看）。

Webhook 表达式的失败会报告给调用方：Hatchet 以 400 状态码拒绝请求，并附带问题描述，例如 `Event key expression must evaluate to a string`。请检查发送 webhook 的系统的投递日志。

幂等键和 event 过滤器的失败最难发现。引擎会在内部记录它们并写入日志，但目前没有任何控制台页面、API 端点或 CLI 命令暴露这些错误。从外部来看，唯一的症状是期望的 run 始终没有出现。如果某个触发悄悄地没有产生 run，而你怀疑是表达式的问题，可以用上面提到的 CEL debug 方法，使用相同的 event payload 或 run 输入来复现该失败。
