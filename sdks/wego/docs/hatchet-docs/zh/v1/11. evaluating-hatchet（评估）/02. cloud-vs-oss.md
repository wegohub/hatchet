# Cloud 与 OSS 对比

Hatchet 有两种提供形式：**Hatchet Cloud**（托管版）和**开源版**（自托管）。两者的编程模型相同：你用代码编写 task/workflow，并运行连接到 Hatchet 的 worker。

本页帮助你选择适合你团队的部署模式。

## 快速决策指南

如果你想要以下内容，请选择 **Hatchet Cloud**：

- 由他人运维 Hatchet 控制平面（升级、扩容、备份）
- 最快上生产环境的路径
- 状态页面和托管的事件响应

如果你需要以下内容，请选择**自托管（OSS）**：

- 对基础设施和网络的完全控制
- 严格的数据驻留要求或隔离网络（air-gapped）环境
- 一个可以用你自己的工具定制和运维的部署

## 两者相同的部分

- **SDK + worker 模型**：你的 worker 运行你的代码并连接到 Hatchet
- **持久化 + 重试**：task 被持久化跟踪，并按配置进行重试
- **可观测性界面**：你可以检查 run、worker 和 workflow 历史
- **核心语义**：相同的 workflow/task/并发模式都适用

## 不同的部分（运维职责）

### Hatchet Cloud（托管版）

由 Hatchet 运行和运维 Hatchet 服务。你需要提供：

- 你的 worker 进程
- 你用于触发 workflow 的应用代码
- 你的运维策略（超时、重试、并发、速率限制）

安全与合规文档请参阅 **[Hatchet Trust Center](https://trust.hatchet.run/)**。当前事件和历史可用性请参阅 **[status.hatchet.run](https://status.hatchet.run/)**。

### 自托管（OSS）

由你运行和运维 Hatchet 服务及其依赖。典型职责包括：

- 供应和扩缩 Hatchet 服务
- 管理 PostgreSQL（以及你部署的任何可选组件）
- 备份、升级和监控
- API/数据库的网络安全和访问控制

## 在 Cloud 与自托管之间迁移

你可以在部署模式之间迁移而无需重写 worker 代码。实际操作中，迁移通常意味着：

- 把 worker 和客户端指向新的端点
- 更换凭证/token
- 校验特定环境的设置（TLS、网络、数据保留等）
