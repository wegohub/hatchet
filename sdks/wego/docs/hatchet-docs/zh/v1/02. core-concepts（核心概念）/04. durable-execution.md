# 持久化执行（Durable Execution）入门

从根本上说，Hatchet 是一个**持久化执行**（durable execution）平台。遗憾的是，durable execution 是一个含义过载、经常令人困惑的术语。如果你刚接触持久化执行，或者想温习一下，我们写了一篇[介绍核心概念的博文](https://hatchet.run/blog/durable-execution)。

在最基本的层面上，持久化执行提供了一组工具，使用得当时，它能为你在 Hatchet 中编写的 task 和 workflow 提供普通任务队列系统无法给出的保障。

## 保障

持久化执行的主要承诺之一（在使用得当时）是让你的 task 获得比传统任务队列更接近[精确一次（exactly-once）语义](https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/)的保证。在实践中，这意味着持久化 task 可以保证你的应用逻辑被正确缓存且重试安全：每当持久化 task 的一部分完成时，它会创建一个新的检查点（持久化事件日志中的一条记录），我们可以从该检查点重放，而无需重新执行实际的应用逻辑。

这意味着，如果你运行一个持久化 task 到中途，而它所在的 worker 崩溃了，你可以从它最后到达的检查点重放该 task，而无需重新运行之前的任何步骤或重复任何工作。对于那些无法合理做到幂等、因而失败后无法重放的系统来说，这一点弥足珍贵。


## 核心假设

Hatchet 持久化执行的核心假设是：持久化 task 只做两类事情：它们可以_等待_某事，例如[等待 sleep 结束](<../06. durable-execution（持久化执行）/03. durable-sleep.md>)或[等待收到 event](<../06. durable-execution（持久化执行）/04. durable-event-waits.md>)；或者它们可以_[派生子 task](<../06. durable-execution（持久化执行）/02. child-spawning.md>)_。这些操作还可以组合，比如让一个持久化 task 等待 sleep 结束_或_ event 被推送，二者取先到者。你可以使用 [or group](<../06. durable-execution（持久化执行）/06. directed-acyclic-graphs.md#waiting-on-conditions-with-or-groups>) 来实现这种行为。

## 示例用途

持久化执行有用的场景很多。几个显而易见的常见选择是：


1. Agentic 工作流，尤其是需要 human-in-the-loop 步骤的工作流——它们在循环中不断派生子任务、收集结果、再派生更多子任务，如此往复。持久化 task 在这里是不二之选，因为它可以从上次中断处重放，既不丢失 agent 之前取得的任何进展，也不需要重放 task 中 human-in-the-loop 的部分（如审批等）。
2. 难以做到幂等的 task，一旦完成就无法重放其中一部分。例如涉及向客户发送邮件，或在执行中途更新表中某个值的操作。
3. 动态工作流，在运行时根据持久化 task 的输入或上游检查点的结果来选择派生哪些子 workflow，从而构建出 DAG。这对支撑拖拽式 DAG 构建器之类的工具尤其有用。
