# 简单的 Task 重试

Hatchet 通过重试策略提供了一种简单而有效的方式来处理 task 中的失败。此功能允许你指定 task 失败后应重试的次数，有助于提升 task 的可靠性和韧性。

> **Info:** task 级别的重试既可用于 `Standalone Tasks`（独立 task），也可用于
>   `Workflow Tasks`。

## 工作原理

当 task 失败时（即抛出错误或返回非零退出码），Hatchet 可以根据 task 对象中定义的 `retries` 配置自动重试该 task。其工作方式如下：

1. 如果 task 失败且 `retries` 设置为大于 0 的值，Hatchet 会捕获错误并重试该 task。
2. task 最多会重试指定的次数，每次重试之间会有短暂的延迟，以避免系统过载。
3. 如果 task 在任何一次重试中成功，task 将正常继续。
4. 如果 task 在耗尽所有指定重试次数后仍然失败，该 task 将被标记为失败。

这种简单的重试机制可以帮助缓解瞬时故障，例如网络问题或外部服务暂时不可用，而无需在 task 代码中编写复杂的错误处理逻辑。

## 如何使用 task 级别重试

要为 task 启用重试，只需在 task 定义的 task 对象中添加 `retries` 属性：

#### Python

```python
@simple_workflow.task(retries=3)
def always_fail(input: EmptyModel, ctx: Context) -> dict[str, str]:
    raise Exception("simple task failed")
```

#### Typescript

```typescript
export const retries = hatchet.task({
  name: 'retries',
  retries: 3,
  fn: async (_, ctx) => {
    throw new Error('intentional failure');
  },
});
```

#### Go

```go
retries := client.NewStandaloneTask("retries-task", func(ctx hatchet.Context, input RetriesInput) (*RetriesResult, error) {
	return nil, errors.New("intentional failure")
}, hatchet.WithRetries(3))
```

#### Ruby

```ruby
SIMPLE_RETRY_WORKFLOW.task(:always_fail, retries: 3) do |input, ctx|
  raise "simple task failed"
end
```

你可以为任何 task 添加 `retries` 属性，Hatchet 会自动处理重试逻辑。

需要注意的是，task 级别重试并不适用于所有类型的失败。例如，如果 task 因编程错误或无效配置而失败，重试该 task 很可能无法解决问题。在这种情况下，你应该修复代码或配置中的底层问题，而不是依赖重试。参见[绕过重试逻辑](#绕过重试逻辑)。

此外，如果 task 与外部服务或数据库交互，在启用重试之前，你应确保该操作是幂等的（即可以安全重复执行而不改变结果）。否则，重试 task 可能导致意外的副作用或数据不一致。

## 在运行中的 task 中获取重试次数

你可以在 task 的上下文对象上获取当前的重试次数：

#### Python

```python
@simple_workflow.task(retries=3)
def fail_twice(input: EmptyModel, ctx: Context) -> dict[str, str]:
    if ctx.retry_count < 2:
        raise Exception("simple task failed")

    return {"status": "success"}
```

#### Typescript

```typescript
export const retriesWithCount = hatchet.task({
  name: 'retries-with-count',
  retries: 3,
  fn: async (_, ctx) => {
    // > Get the current retry count
    const retryCount = ctx.retryCount();

    ctx.logger.info(`Retry count: ${retryCount}`);

    if (retryCount < 2) {
      throw new Error('intentional failure');
    }

    return {
      message: 'success',
    };
  },
});
```

#### Go

```go
retriesWithCount := client.NewStandaloneTask("fail-twice-task", func(ctx hatchet.Context, input RetriesWithCountInput) (*RetriesWithCountResult, error) {
	// Get the current retry count
	retryCount := ctx.RetryCount()

	fmt.Printf("Retry count: %d\n", retryCount)

	if retryCount < 2 {
		return nil, errors.New("intentional failure")
	}

	return &RetriesWithCountResult{
		Message: "success",
	}, nil
}, hatchet.WithRetries(3))
```

#### Ruby

```ruby
SIMPLE_RETRY_WORKFLOW.task(:fail_twice, retries: 3) do |input, ctx|
  raise "simple task failed" if ctx.retry_count < 2

  { "status" => "success" }
end
```

## 指数退避

Hatchet 还支持重试的指数退避（exponential backoff），这有助于以更具韧性的方式处理失败。指数退避会让重试之间的延迟按指数增长，让失败的服务在下一次重试前有更多时间恢复。

#### Python

```python
@backoff_workflow.task(
    retries=10,
    # 👀 Maximum number of seconds to wait between retries
    backoff_max_seconds=10,
    # 👀 Factor to increase the wait time between retries.
    # This sequence will be 2s, 4s, 8s, 10s, 10s, 10s... due to the maxSeconds limit
    backoff_factor=2.0,
)
def backoff_task(input: EmptyModel, ctx: Context) -> dict[str, str]:
    if ctx.retry_count < 3:
        raise Exception("backoff task failed")

    return {"status": "success"}
```

#### Typescript

```typescript
export const withBackoff = hatchet.task({
  name: 'with-backoff',
  retries: 10,
  backoff: {
    // 👀 Maximum number of seconds to wait between retries
    maxSeconds: 10,
    // 👀 Factor to increase the wait time between retries.
    // This sequence will be 2s, 4s, 8s, 10s, 10s, 10s... due to the maxSeconds limit
    factor: 2,
  },
  fn: async () => {
    throw new Error('intentional failure');
  },
});
```

#### Go

```go
withBackoff := client.NewStandaloneTask("with-backoff-task", func(ctx hatchet.Context, input BackoffInput) (*BackoffResult, error) {
	return nil, errors.New("intentional failure")
}, hatchet.WithRetries(3), hatchet.WithRetryBackoff(2, 10))
```

#### Ruby

```ruby
BACKOFF_WORKFLOW.task(
  :backoff_task,
  retries: 10,
  # Maximum number of seconds to wait between retries
  backoff_max_seconds: 10,
  # Factor to increase the wait time between retries.
  # This sequence will be 2s, 4s, 8s, 10s, 10s, 10s... due to the maxSeconds limit
  backoff_factor: 2.0
) do |input, ctx|
  raise "backoff task failed" if ctx.retry_count < 3

  { "status" => "success" }
end
```

## 绕过重试逻辑

各 Hatchet SDK 都暴露了一个 `NonRetryable` 异常，允许你绕过 task 上预先配置的重试逻辑。**如果你的 task 抛出此异常，它将不会被重试。** 这让你在不想或无法安全重试的情况下绕过默认的重试行为。适用场景包括：

1. 调用外部 API 并收到 4XX 响应码的 task。
2. 包含单个非幂等操作的 task，该操作可能失败但失败后无法安全重跑，例如计费操作。
3. 需要人工介入才能解决的失败。

#### Python

```python
@non_retryable_workflow.task(retries=1)
def should_not_retry(input: EmptyModel, ctx: Context) -> None:
    raise NonRetryableException("This task should not retry")
```

#### Typescript

```typescript
const shouldNotRetry = nonRetryableWorkflow.task({
  name: 'should-not-retry',
  fn: () => {
    throw new NonRetryableError('This task should not retry');
  },
  retries: 1,
});
```

#### Go

```go
retries := client.NewStandaloneTask("non-retryable-task", func(ctx hatchet.Context, input NonRetryableInput) (*NonRetryableResult, error) {
	return nil, hatchet.NewNonRetryableError(errors.New("intentional failure"))
}, hatchet.WithRetries(3))
```

#### Ruby

```ruby
NON_RETRYABLE_WORKFLOW.task(:should_not_retry, retries: 1) do |input, ctx|
  raise Hatchet::NonRetryableError, "This task should not retry"
end

NON_RETRYABLE_WORKFLOW.task(:should_retry_wrong_exception_type, retries: 1) do |input, ctx|
  raise TypeError, "This task should retry because it's not a NonRetryableError"
end

NON_RETRYABLE_WORKFLOW.task(:should_not_retry_successful_task, retries: 1) do |input, ctx|
  # no-op
end
```

在这些情况下，即使 `retries` 被设为非零值（即通常 task 会重试），Hatchet 也不会重试。

## Python SDK 客户端重试行为

上文描述的重试行为针对的是 Hatchet 内部的 task 执行。Python SDK 对 SDK 自身发起的某些客户端 REST 和 gRPC 调用还有单独的重试行为。

这些客户端重试与 task 重试是分开配置的，并不控制 task 在 worker 中失败后是否重试。

> **Info:** task 重试与 SDK 客户端重试是两个独立的机制。task 重试控制 Hatchet 是否
>   在 task 失败后重试该 task；SDK 客户端重试控制 Python SDK 是否对某些
>   指向 Hatchet 的 API 调用进行重试。

### 默认客户端重试行为

默认情况下，Python SDK 会对某些客户端调用使用指数退避进行重试，`max_attempts` 默认为 5。

**REST API 调用**

错误类型, 默认是否重试

| HTTP 5xx（服务器错误） | 是 |
| --- | --- |
| HTTP 404（未找到） | 是 |
| HTTP 429（请求过多） | 否 |
| HTTP 400、401、403、409、422（客户端错误） | 否 |
| 传输错误（超时、连接、TLS、协议） | 否 |

**gRPC 调用**

| 状态码 | 是否重试 |
| --- | --- |
| `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `INTERNAL` | 是 |
| `RESOURCE_EXHAUSTED`, `ABORTED`, `UNKNOWN` | 是 |
| `UNIMPLEMENTED`, `NOT_FOUND`, `INVALID_ARGUMENT` | 否 |
| `ALREADY_EXISTS`, `UNAUTHENTICATED`, `PERMISSION_DENIED` | 否 |

> **Info:** REST 404 响应默认会被重试，是因为某些 REST 读取可能会观察到核心数据库
>   与 OLAP 数据库之间的复制延迟。

### 配置 Python SDK 客户端重试

Python SDK 通过 `TenacityConfig` 暴露客户端重试配置，可直接在 `ClientConfig` 中设置，也可通过环境变量设置。

```python
import os

from hatchet_sdk import Hatchet
from hatchet_sdk.config import ClientConfig, HTTPMethod, TenacityConfig

hatchet = Hatchet(
    config=ClientConfig(
        token=os.environ["HATCHET_CLIENT_TOKEN"],
        tenacity=TenacityConfig(
            max_attempts=5,
            retry_429=False,
            retry_transport_errors=False,
            retry_transport_methods=[HTTPMethod.GET, HTTPMethod.DELETE],
        ),
    )
)
```

| 名称 | 类型 | 说明 | 默认值 |
| --- | --- | --- | --- |
| `max_attempts` | `int` | 最大重试次数。设为 0 可禁用重试。 | `5` |
| `retry_429` | `bool` | 对 HTTP 429 Too Many Requests 响应启用重试。 | `False` |
| `retry_transport_errors` | `bool` | 对 REST 传输层错误（超时、连接、TLS）启用重试。 | `False` |
| `retry_transport_methods` | `list[HTTPMethod]` | 启用 `retry_transport_errors` 时，遇到传输错误要重试的 HTTP 方法。 | `[GET, DELETE]` |

你也可以通过环境变量进行配置：

| 环境变量 | 说明 |
| --- | --- |
| `HATCHET_CLIENT_TENACITY_MAX_ATTEMPTS` | 最大重试次数 |
| `HATCHET_CLIENT_TENACITY_RETRY_429` | 启用 429 重试（`true`/`false`） |
| `HATCHET_CLIENT_TENACITY_RETRY_TRANSPORT_ERRORS` | 启用传输错误重试（`true`/`false`） |

### 幂等性注意事项

> **Warning:** 启用 `retry_transport_errors` 时，默认只重试幂等的 HTTP 方法（`GET`、
>   `DELETE`）。非幂等方法（`POST`、`PUT`、`PATCH`）被排除在外，因为在传输错误后
>   重试它们可能导致重复操作 —— 如果原始请求实际已成功但响应丢失的话。

你可以将非幂等方法加入 `retry_transport_methods`，但仅在以下情况才可以：

1. 你的操作是幂等的（例如使用了幂等键），或者
2. 你理解并接受重复操作的风险

### 重试时机

Python SDK 客户端重试使用带抖动的指数退避。目前无法通过 `TenacityConfig` 对退避时机进行细粒度配置。

## Go SDK 客户端重试行为

上文描述的重试行为针对的是 Hatchet 内部的 task 执行。Go SDK 对 SDK 自身向 Hatchet 发起的某些 REST 和 gRPC 调用也会重试。

这些 SDK 客户端重试与 task 重试是分开配置的。它们并不控制 Hatchet 是否在 task 于 worker 中失败后重试该 task。

> **Info:** task 重试与 SDK 客户端重试是两个独立的机制。task 重试控制 Hatchet 是否
>   在 task 失败后重试该 task；SDK 客户端重试控制 Go SDK 是否对某些
>   指向 Hatchet 的 API 调用进行重试。

### 默认 Go 客户端重试行为

默认情况下，Go SDK 对某些客户端调用使用指数退避进行重试。REST 读取最多使用 5 次总尝试：首次尝试加最多 4 次重试。gRPC 调用保持现有的 5 次尝试重试上限。

REST 读取重试使用有界的抖动退避。当调用方请求上下文没有截止时间时，每次 REST 尝试使用响应头超时，且不会截断响应体读取。如果调用方上下文已有截止时间，则整个请求受该截止时间约束。

**REST API 调用（仅限无 body 的 `GET` 和 `HEAD`）**

错误类型, 默认是否重试

| HTTP 502、503、504（网关错误） | 是 |
| --- | --- |
| HTTP 404（未找到） | 否 |
| HTTP 429（请求过多） | 是 |
| HTTP 400、401、403、409、422（客户端错误） | 否 |
| 传输错误（超时、连接、TLS、协议） | 是 |

对于幂等读取上的 HTTP 429 响应，Go SDK 会在有效且不超过客户端重试上限时遵循 `Retry-After` 响应头。当 `Retry-After` 缺失、无效或过大时，退回到与其他可重试错误相同的有界抖动退避。

> **Info:** 与 Python SDK 不同，本版本中 Go SDK 不会对 REST 读取的 HTTP 404 响应重试。
>   Python 重试某些 404 读取是为了应对核心数据库与 OLAP 数据库之间的复制延迟。

**gRPC 调用**

| 状态码 | 是否重试 |
| --- | --- |
| `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `INTERNAL` | 是 |
| `RESOURCE_EXHAUSTED` | 是 |
| `FAILED_PRECONDITION` | 否 |
| `UNIMPLEMENTED`, `NOT_FOUND`, `INVALID_ARGUMENT` | 否 |
| `ALREADY_EXISTS`, `UNAUTHENTICATED`, `PERMISSION_DENIED` | 否 |

> **Info:** `FAILED_PRECONDITION` 不会被重试，因为 Hatchet 用它表示非瞬时的控制平面
>   信号，例如不活跃的监听器。在本版本中，一元拦截器仍会重试所有一元 RPC，包括写操作。

### 配置 Go SDK 客户端重试

使用环境变量可禁用 SDK 客户端重试：

环境变量, 说明

`HATCHET_CLIENT_NO_RETRY`, 设为真值时同时禁用 REST 和 gRPC 的 SDK 客户端重试。
`HATCHET_CLIENT_NO_GRPC_RETRY`, 旧版的仅 gRPC 重试控制。只禁用 gRPC SDK 重试。除非设置了 `HATCHET_CLIENT_NO_RETRY`，REST 读取重试保持启用。

如果两个变量都设置了，所有 SDK 客户端重试都将被禁用。

### 幂等性注意事项

> **Warning:** Go SDK 的 REST 重试仅适用于无 body 的 `GET` 和 `HEAD` 请求。本版本中，
>   SDK 客户端从不重试 `POST`、`PUT`、`PATCH` 和 `DELETE` 请求。带 body 的请求被排除
>   是因为 Go 的 `http.Request` body 是一次性的，除非设置了 `GetBody` 或 SDK 对 body
>   进行缓冲并重建。生成的 REST 客户端没有设置 `GetBody`。

## 总结

Hatchet 的 task 级别重试功能是处理 task 瞬时故障的一种简单有效的方式，可以提升 task 的可靠性和韧性。通过为每个 task 指定重试次数，你可以确保 task 能从临时问题中恢复，而无需复杂的错误处理逻辑。

请谨慎使用重试，且仅对幂等的 task 使用。对于更高级的重试策略（如指数退避或熔断），请持续关注 Hatchet 重试能力的后续更新。
