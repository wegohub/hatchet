# 调试 Hatchet Run

以下是供 AI agent 诊断 Hatchet run 失败、卡住或行为异常的指令。请按顺序执行每个步骤。

这些命令需要 profile。本地开发时 worker 可以改用 embedded 模式运行（参见 `local-dev-embedded.md`）；embedded run 请通过代码或 `hatchet embedded-ui` 检查。

## 步骤 1：获取 Run 状态

```bash
hatchet runs get RUN_ID -o json -p HATCHET_PROFILE
```

检查 JSON 响应：

- `.run.status` —— 整体 run 状态（`QUEUED`、`RUNNING`、`COMPLETED`、`FAILED`、`CANCELLED`）
- `.run.displayName` —— workflow 名称
- `.run.input` —— 触发 workflow 时提供的输入
- `.tasks[]` —— run 中的每个 task，各自带有 `status`、`displayName` 以及 `output` 或 `errorMessage`
- `.tasks[].startedAt` 和 `.tasks[].finishedAt` —— 时间信息

## 步骤 2：获取事件日志

```bash
hatchet runs events RUN_ID -o json -p HATCHET_PROFILE
```

事件日志展示 run 的完整生命周期。每个事件包含：

- `eventType` —— 发生了什么（例如 `QUEUED`、`STARTED`、`FINISHED`、`FAILED`、`CANCELLED`）
- `message` —— 人类可读的描述
- `taskDisplayName` —— 事件属于哪个 task
- `timestamp` —— 发生时间

按时间顺序阅读事件，以理解事件的发生顺序。

## 步骤 3：获取日志

```bash
hatchet runs logs RUN_ID -p HATCHET_PROFILE
```

这会打印 task 代码的应用级别日志输出（例如 print 语句、logger 调用）。对于多 task（DAG）run，所有 task 的日志会按时间戳合并排序，并带有 task 名称前缀。

## 诊断速查表

### Task 卡在 QUEUED（没有 STARTED 事件）

task 从未被 worker 接取。可能的原因：

- **没有 worker 在运行。**用 `hatchet worker dev -p HATCHET_PROFILE` 启动一个。
- **worker 没有注册此 task 类型。**workflow 定义中的 task 名称必须与 worker 代码注册的匹配。检查 worker 启动日志。
- **worker 连接到了不同的租户/profile。**验证 worker 和触发使用相同的 `-p` profile。

### Task FAILED

检查步骤 3 的日志输出中的堆栈跟踪或错误消息。常见原因：

- task 代码中未处理的异常。
- 超时。
- 依赖项（数据库、API 等）不可达。

步骤 2 的事件会显示带有错误消息的 `FAILED` 事件。

### Task CANCELLED

检查事件中的 `CANCELLED` 事件。message 字段指示取消来源：

- 通过仪表盘或 CLI 手动取消。
- 父 workflow 取消（针对 DAG workflow）。
- 基于超时的取消。

### Run COMPLETED 但输出不对

如果 run 已完成但产生了意外结果：

1. 检查 run 状态（步骤 1）中的 `.tasks[].output`，查看每个 task 返回了什么。
2. 检查日志（步骤 3）以追踪执行流程。
3. 检查 `.run.input` 以验证是否提供了正确的输入。

### 执行缓慢

比较步骤 1 中每个 task 的 `startedAt` 和 `finishedAt` 时间戳，以确定哪个 task 是瓶颈。检查 run 被触发到第一个 task 开始之间是否存在较长间隔（表明排队延迟，可能由 worker 容量导致）。
