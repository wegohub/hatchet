# Kubernetes 网络

## 概述

默认情况下，Kubernetes Helm chart 不会通过 ingress 暴露任何 Hatchet 服务。有三个服务可能需要暴露：

1. `hatchet-engine`
2. `hatchet-stack-api`
3. `hatchet-stack-frontend`

要暴露这些服务，你需要完成以下步骤：

1. 为 `frontend` 和 `engine` 服务配置 ingress（以及可选的 `api` 服务）。我们建议将 ingress 配置为把 `/api` 端点反向代理到 `hatchet-stack-api` 服务，并配置单独的 ingress 代理到 `hatchet-engine`。

2. 更新以下配置变量：

```yaml
api:
  env:
    SERVER_AUTH_COOKIE_DOMAIN: "hatchet.example.com" # example.com should be replaced with your domain
    SERVER_URL: "https://hatchet.example.com" # example.com should be replaced with your domain
    SERVER_GRPC_BIND_ADDRESS: "0.0.0.0"
    SERVER_GRPC_INSECURE: "false"
    SERVER_GRPC_BROADCAST_ADDRESS: "hatchet-engine.example.com:443" # example.com should be replaced with your domain

engine:
  env:
    SERVER_AUTH_COOKIE_DOMAIN: "hatchet.example.com" # example.com should be replaced with your domain
    SERVER_URL: "https://hatchet.example.com" # example.com should be replaced with your domain
    SERVER_GRPC_BIND_ADDRESS: "0.0.0.0"
    SERVER_GRPC_INSECURE: "false"
    SERVER_GRPC_BROADCAST_ADDRESS: "engine.hatchet.example.com:443" # example.com should be replaced with your domain
```

## 在 URL 子路径下提供 Hatchet 服务

默认情况下，仪表盘假定自己是从主机的根路径提供服务的（例如 `https://hatchet.example.com/`）。如果你需要将其托管在反向代理后面的子路径下（例如 `https://example.com/hatchet/`），请设置前端基础路径（base path），使仪表盘相对于该子路径渲染链接、资源和客户端路由。

基础路径会在请求时注入到所服务的 `index.html` 中，静态文件服务器会在该子路径下提供应用（资源和客户端路由），因此单个镜像无需重新构建前端即可适用于任何子路径——也不需要做前缀重写的代理。

### 配置基础路径

根据你的部署模式，通过环境变量设置基础路径。默认值为 `/`，即保持根路径托管的行为。

部署方式，变量，说明

Helm `frontend` chart，`BASE_PATH`，在 `frontend.env` 下设置。传递给静态文件服务器。
合并的 `dashboard` 镜像，`BASE_PATH`，由 entrypoint 注入到 `index.html` 和 nginx 路由中。
`hatchet-lite`，`LITE_FRONTEND_BASE_PATH`
`hatchet-staticfileserver` 二进制，`-base-path` 标志

> **Info:** 基础路径会自动规范化，因此 `hatchet`、`/hatchet` 和 `/hatchet/`
>   都是等价的——仪表盘的相对资源 URL 始终会在子路径下正确解析。

### 反向代理要求

静态文件服务器本身就在基础路径下提供应用，因此代理只需**原样转发请求，不做路径重写**。当前端和 API 位于同一主机后面时，需要两条路由规则：

1. **将子路径原样转发给前端。**前端本身已经在 `/hatchet` 下提供其资源和 SPA 路由，因此不需要 `rewrite-target` / `handle_path` 之类的前缀剥离——普通的反向代理即可。
2. **保持 `/api` 在主机根路径。**仪表盘会向绝对的 `/api/...` 路径发起 API 请求，这些路径不受基础路径影响。不要把 API 移到子路径下——将 `/api/*` 直接路由到 API 服务。

使用 chart 内置的 Caddy 代理时，`Caddyfile` 如下：

```caddyfile
example.com {
    handle /api/* {
        reverse_proxy hatchet-stack-api:8080
    }

    # No prefix stripping — the frontend serves the app under /hatchet itself
    handle /hatchet/* {
        reverse_proxy hatchet-stack-frontend:8080
    }
}
```

将 `frontend.env.BASE_PATH` 设为 `/hatchet` 后，仪表盘可通过 `https://example.com/hatchet/` 访问，API 调用继续发往 `https://example.com/api/...`。对于 `hatchet-lite` 这样的单服务部署，只需设置基础路径即可——lite 会直接在子路径下提供仪表盘，无需单独的代理。

使用独立 **nginx** 反向代理的等效配置——同样，两个 location 都不做路径重写：

```nginx
server {
    listen 80;
    server_name example.com;

    location /api/ {
        proxy_pass http://hatchet-stack-api:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /hatchet {
        return 301 /hatchet/;
    }

    location /hatchet/ {
        proxy_pass http://hatchet-stack-frontend:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

在 Kubernetes 上使用 `ingress-nginx` 控制器时，同样的路由是单个 Ingress 上的两条 `Prefix` 路径——尤其**不需要 `nginx.ingress.kubernetes.io/rewrite-target` 注解**，因为前端本身就会提供该子路径：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hatchet
spec:
  ingressClassName: nginx
  rules:
    - host: example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: hatchet-stack-api
                port:
                  number: 8080
          - path: /hatchet
            pathType: Prefix
            backend:
              service:
                name: hatchet-stack-frontend
                port:
                  number: 8080
```

## 示例：`nginx-ingress`

让我们通过一个示例来介绍如何通过 `hatchet.example.com`（用于 API 和前端）和 `engine.hatchet.example.com`（用于 engine）暴露 Hatchet。

我们将以启用 SSL 的方式部署，这需要有效的证书。我们建议使用 [cert-manager](https://cert-manager.io/docs/) 来管理证书。本指南假设你已配置了名为 `letsencrypt-prod` 的 cert-manager `ClusterIssuer`。

以下是此设置的 `values.yaml` 文件示例：

```yaml
api:
  env:
    # TODO: insert these values from the output of the keyset generation command
    SERVER_AUTH_COOKIE_SECRETS: "$SERVER_AUTH_COOKIE_SECRET1 $SERVER_AUTH_COOKIE_SECRET2"
    SERVER_ENCRYPTION_MASTER_KEYSET: "$SERVER_ENCRYPTION_MASTER_KEYSET"
    SERVER_ENCRYPTION_JWT_PRIVATE_KEYSET: "$SERVER_ENCRYPTION_JWT_PRIVATE_KEYSET"
    SERVER_ENCRYPTION_JWT_PUBLIC_KEYSET: "$SERVER_ENCRYPTION_JWT_PUBLIC_KEYSET"
    SERVER_AUTH_COOKIE_DOMAIN: "hatchet.example.com" # example.com should be replaced with your domain
    SERVER_URL: "https://hatchet.example.com" # example.com should be replaced with your domain
    SERVER_GRPC_BIND_ADDRESS: "0.0.0.0"
    SERVER_GRPC_INSECURE: "false"
    SERVER_GRPC_BROADCAST_ADDRESS: "engine.hatchet.example.com:443" # example.com should be replaced with your domain

engine:
  env:
    # TODO: insert these values from the output of the keyset generation command
    SERVER_AUTH_COOKIE_SECRETS: "$SERVER_AUTH_COOKIE_SECRET1 $SERVER_AUTH_COOKIE_SECRET2"
    SERVER_ENCRYPTION_MASTER_KEYSET: "$SERVER_ENCRYPTION_MASTER_KEYSET"
    SERVER_ENCRYPTION_JWT_PRIVATE_KEYSET: "$SERVER_ENCRYPTION_JWT_PRIVATE_KEYSET"
    SERVER_ENCRYPTION_JWT_PUBLIC_KEYSET: "$SERVER_ENCRYPTION_JWT_PUBLIC_KEYSET"
    SERVER_AUTH_COOKIE_DOMAIN: "hatchet.example.com" # example.com should be replaced with your domain
    SERVER_URL: "https://hatchet.example.com" # example.com should be replaced with your domain
    SERVER_GRPC_BIND_ADDRESS: "0.0.0.0"
    SERVER_GRPC_INSECURE: "false"
    SERVER_GRPC_BROADCAST_ADDRESS: "engine.hatchet.example.com:443" # example.com should be replaced with your domain
  ingress:
    enabled: true
    ingressClassName: nginx
    labels: {}
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
      nginx.ingress.kubernetes.io/auth-tls-verify-client: "optional"
      nginx.ingress.kubernetes.io/auth-tls-secret: "${kubernetes_namespace.cloud.metadata[0].name}/engine-cert"
      nginx.ingress.kubernetes.io/auth-tls-verify-depth: "1"
      nginx.ingress.kubernetes.io/auth-tls-pass-certificate-to-upstream: "true"
      nginx.ingress.kubernetes.io/backend-protocol: "GRPC"
      nginx.ingress.kubernetes.io/ssl-redirect: "true"
      nginx.ingress.kubernetes.io/grpc-backend: "true"
      nginx.ingress.kubernetes.io/server-snippet: |
        grpc_read_timeout 1d;
        grpc_send_timeout 1h;
        client_header_timeout 1h;
        client_body_timeout 1h;
    hosts:
      - host: engine.hatchet.example.com
        paths:
          - path: /
        backend:
          serviceName: hatchet-engine
          servicePort: 7070
    tls:
      - hosts:
          - engine.hatchet.example.com
        secretName: engine-cert
        servicePort: 7070

frontend:
  ingress:
    enabled: true
    ingressClassName: nginx
    labels: {}
    annotations:
      nginx.ingress.kubernetes.io/proxy-body-size: 50m
      nginx.ingress.kubernetes.io/proxy-send-timeout: "60"
      nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
      nginx.ingress.kubernetes.io/proxy-connect-timeout: "60"
      cert-manager.io/cluster-issuer: letsencrypt-prod
    hosts:
      - host: hatchet.example.com
        paths:
          - path: /api
            backend:
              serviceName: hatchet-api
              servicePort: 8080
          - path: /
            backend:
              serviceName: hatchet-frontend
              servicePort: 8080
    tls:
      - secretName: hatchet-api
        hosts:
          - hatchet.example.com
```
