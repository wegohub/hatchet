# 升级与降级 Hatchet

本指南介绍如何安全地升级和降级自托管的 Hatchet 实例，并针对生产关键型工作负载提供策略。

## 概述

对于生产关键型部署，我们推荐以下工作流程：

1. 升级前对数据库拍**快照**
2. 将 Hatchet engine **升级**到新版本
3. **验证**升级按预期工作
4. 如果出现问题，通过恢复快照或运行 down migration 来**降级**

## 步骤 1：拍摄数据库快照

在进行任何版本变更之前，请为数据库创建一个时间点快照。这样在升级引发问题时，你就有了一条快速可靠的回滚路径。

请参阅你的数据库提供商的备份和恢复文档：

- **PostgreSQL（自管理）：**[Backup and Restore](https://www.postgresql.org/docs/current/backup.html)
- **AWS RDS：**[Backing Up and Restoring](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_CommonTasks.BackupRestore.html)
- **Google Cloud SQL：**[Backup and Recovery](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups)
- **Azure Database for PostgreSQL：**[Backup](https://learn.microsoft.com/en-us/azure/backup/backup-azure-database-postgresql)

## 步骤 2：升级 Engine 版本

快照就绪后，升级 Hatchet engine。

> **Info:** Hatchet 会在 engine 启动时自动运行数据库 migration。升级时不需要
>   单独的 migration 步骤。

### Docker Compose

更新你的 `docker-compose.yml` 中的镜像标签：

```yaml
services:
  hatchet-engine:
    image: ghcr.io/hatchet-dev/hatchet/hatchet-engine:v0.78.26
    # ... rest of configuration

  hatchet-dashboard:
    image: ghcr.io/hatchet-dev/hatchet/hatchet-dashboard:v0.78.26
    # ... rest of configuration
```

然后重新部署：

> **Warning:** 在容器恢复运行之前，这会导致一些停机时间。

```bash
docker-compose pull
docker-compose down
docker-compose up -d
```

### Kubernetes（Helm）

Hatchet Helm chart 使用 `sharedConfig.image.tag` 值来设置所有组件（engine、API、前端、migration）的镜像标签。将其设置为目标 Hatchet 版本：

```yaml
# values.yaml
sharedConfig:
  image:
    tag: "v0.78.26"
```

然后升级 release：

```bash
# hatchet-stack (standard deployment)
helm upgrade hatchet ./charts/hatchet-stack \
  --namespace hatchet \
  --values values.yaml

# hatchet-ha (high-availability deployment)
helm upgrade hatchet ./charts/hatchet-ha \
  --namespace hatchet \
  --values values.yaml
```

> **Info:** 你也可以覆盖单个组件的标签（例如 `engine.image.tag`、
>   `frontend.image.tag`），但设置 `sharedConfig.image.tag` 时它优先。

### 验证

升级后，验证部署是否健康：

1. 检查 engine 是否正在运行并接受连接
2. 确认仪表盘能加载并显示正确的版本
3. 运行一个测试 workflow 验证端到端功能
4. 监控日志中是否有 migration 错误或意外警告

```bash
# Docker Compose
docker-compose logs hatchet-engine | head -50

# Kubernetes
kubectl logs -n hatchet -l app=hatchet-engine --tail=50
```

## 步骤 3：必要时降级

如果升级引发了问题，根据你的情况有两种选择：

> **Warning:** 以下两种方案都会导致数据丢失和一定的停机时间。

### 方案 A：从数据库快照恢复（生产环境推荐）

这是最快、最安全的回滚路径。它将数据库恢复到升级前的确切状态，避免了 down migration 不完整的风险。


### 停止所有 Hatchet 服务

关闭所有 Hatchet engine 实例，以防止恢复期间发生写入。

```bash
# Docker Compose
docker-compose down

# Kubernetes
kubectl scale deployment hatchet-engine -n hatchet --replicas=0
```

### 恢复数据库快照

按照你的数据库提供商的恢复流程操作（相关文档链接见[步骤 1](#step-1-take-a-database-snapshot)）。

### 部署先前的 Hatchet 版本

将你的部署更新为使用先前版本的镜像标签（相关部署方式参见[升级 Engine 版本](#step-2-upgrade-engine-versions)）并重新部署。

### 验证回滚

确认 engine 启动、仪表盘加载，且 workflow 正确执行。


### 方案 B：运行 Down Migration（手动）

如果你没有数据库快照，或希望进行更有针对性的回滚，可以运行 down migration 来回退 schema 变更。详细说明请参阅[手动降级数据库 Schema](<19. downgrading-db-schema-manually.md>)指南，包括：

- 为目标 Hatchet 版本查找目标 migration 版本
- 运行 `hatchet-migrate --down <migration_version>`
- 部署较旧的 engine 版本

> **Warning:** Down migration 可能无法完全逆转所有数据变更（例如被删除的列
>   数据会丢失）。对于生产关键型工作负载，尽可能优先选择从快照恢复。
