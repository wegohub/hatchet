# Hatchet 性能调优

一般来说，配备合理的数据库实例（4 CPU、8GB RAM）且 payload 较小时，Hatchet 可以处理每秒数百个事件和 workflow run。但随着吞吐量的增加，你会开始看到性能下降。性能下降最常见的原因如下所列。

## 数据库连接池

默认的最大连接池大小为每个 engine 实例 50 个。如果吞吐量较高，你可能需要增大该值。可以通过 engine 上的 `DATABASE_MAX_CONNS` 环境变量进行设置。注意，如果增大该值，你还需要相应增大 Postgres 实例上的 [`max_connections`](https://www.postgresql.org/docs/current/runtime-config-connection.html) 值。

## 数据库 CPU 过高

由于 Hatchet 工作负载的特性，你在数据库上通常首先遇到的瓶颈是 CPU。如果你能查看数据库查询性能指标，值得排查 CPU 高企的原因。如果某个查询存在严重的锁争用，请告知 Hatchet 团队，我们正致力于在未来的版本中减少锁争用。否则，如果 CPU 使用率很高但没有任何锁争用，你应该增加数据库实例的核心数。

如果你在执行大量插入操作（尤其是在短时间内），并且这与高 CPU 使用率相关，可以通过使用批量端点或调优缓冲区设置来提升性能。

### 使用批量端点

启动 workflow 主要有两种方式：向 Hatchet 发送事件，以及直接启动 workflow。在大多数示例 workflow 中，我们一次推送一个事件或 workflow，但也可以在一个请求中发送多个事件或 workflow。

#### 事件

 #### Python

```python
hatchet.event.bulk_push(
    events=[
        BulkPushEventWithMetadata(
            key="user:create",
            payload={"userId": str(i), "should_skip": False},
        )
        for i in range(10)
    ]
)
```

w.RegisterWorkflow(

        Steps: []*worker.WorkflowStep{

### 调优缓冲区设置

Hatchet 会对消息队列写入进行批处理，以减少到 broker 和数据库的往返次数。以下是发布（ outgoing）和订阅（incoming）缓冲区的默认设置，它们按 `(queue, tenant, message)` 对消息进行批处理：

```sh
# Max messages a buffer accumulates before flushing early (default: 10)
SERVER_DEFAULT_BUFFER_SIZE=10

# How long a buffer waits before flushing what it has accumulated (default: 10ms)
SERVER_DEFAULT_BUFFER_FLUSH_INTERVAL=10ms

# Max concurrent in-flight flushes (default: 1 for the publish buffer, 10 for the subscribe buffer)
SERVER_DEFAULT_BUFFER_CONCURRENCY=10
```

更大的缓冲区大小和更长的刷新间隔会在每次写入时批处理更多工作，从而以少量延迟增加为代价降低 broker 和数据库负载。建议在你自己的基础设施上进行基准测试和调优，以为你的工作负载和使用场景找到最优值。

> **Info:** 这些是默认值。一些内部订阅者固定了自己的值：共享的
>   租户读取器（tenant reader）固定了刷新间隔和并发数，因此只有
>   `SERVER_DEFAULT_BUFFER_SIZE` 会影响它。

## 启动缓慢

吞吐量较高时，你可能会看到 workflow 中每个 step run 的启动时间变慢。原因通常是每个 step run 在发送给 worker 之前需要先在内部消息队列中处理。你可以通过设置以下环境变量来提高该内部队列的吞吐量（默认值为 `100`）：

```
SERVER_MSGQUEUE_RABBITMQ_QOS=200
```

请注意，该值表示可并行处理的消息数，每条消息通常对应至少一次数据库写入，因此如果该值显著高于 `DATABASE_MAX_CONNS`，性能不会有提升。如果你在 engine 日志中看到连接饱和的警告，请考虑降低该值。

## 数据库设置与 Autovacuum

在若干场景下，可能需要修改 Postgres 参数以提升性能。默认情况下，每个 workflow run 和 step run 都会在 Postgres 实例中保留 30 天。如果不调优 autovacuum 设置，你可能会看到许多表出现严重的表膨胀。如果你存储的 workflow run 或 step run 数据超过 500 GB，我们建议采用以下 autovacuum 设置以更激进地执行 autovacuum：

```
autovacuum_max_workers=10
autovacuum_vacuum_scale_factor=0.1
autovacuum_analyze_scale_factor=0.05
autovacuum_vacuum_threshold=25
autovacuum_analyze_threshold=25
autovacuum_vacuum_cost_delay=10
autovacuum_vacuum_cost_limit=1000
```

如果你的数据库内存充足，可能需要增大 `work_mem` 或 `maintenance_work_mem` 值。例如，在可用内存充足的数据库实例上，我们通常设置以下值：

```
maintenance_work_mem=2147483647
work_mem=125828
```

此外，如果磁盘容量充足，设置以下参数可能会提升性能：

```
max_wal_size=15040
```

## 扩展 Hatchet Engine

默认情况下，Hatchet engine 在单个实例上运行所有内部服务。Hatchet engine 上的内部服务如下：

- **grpc-api**：Hatchet engine 的 gRPC 端点。这是 Hatchet worker 的主要端点。不要与 Hatchet REST API 混淆，后者是一个独立的服务，我们通常称之为 `api`。
- **controllers**：管理 workflow run、step run 和事件生命周期的内部服务。该服务对数据库写入密集，对消息队列读取密集。
- **scheduler**：将 step run 调度给 worker 的内部服务。该服务对数据库的读取和写入都很密集。

可以通过运行多个 engine 实例对 Hatchet engine 进行水平扩展。但是，如果在同一 engine 实例上运行其他服务时看到 scheduler 产生大量警告，我们建议将 scheduler 运行在单独的实例上。有关如何在单独实例上运行 scheduler 的更多信息，请参阅[高可用](<11. high-availability.md>)文档。
