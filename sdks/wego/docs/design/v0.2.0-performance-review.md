## 一、热路径分析

### 1.1 关键路径识别

**路径 1：客户端发送 → 任务执行 → 输出消费**
```
Client SendMsg → 编码 envelope → 保存快照
       ↓
CloseSend → 批量提交 → 发布 CLAIM
       ↓
Worker 读回 CLAIM → 确认获胜 → 启动 handler
       ↓
Handler 输出 → 编码帧 → 发布 DATA
       ↓
Client 订阅 → 解码帧 → 状态机解释 → RecvMsg 交付
```

**路径 2：恢复订阅**
```
ResumeStream → 验证历史起点 → 扫描到 checkpoint
       ↓
继续订阅 → 解码 → 状态机 → 交付
```

## 二、性能优势

### 2.1 并发设计 ✅ **优秀 (5/5)**

**独立锁避免竞争**：
```go
// taskClientStream：发送和接收独立
type taskClientStream struct {
    sendMu  sync.Mutex  // 只保护输入方向
    recvMu  sync.Mutex  // 只保护输出方向
    mu      sync.Mutex  // 保护接收状态
}
```

✅ **优点**：
- SendMsg 和 RecvMsg 不相互阻塞
- 客户端可以边发送边接收
- 减少锁等待时间

**网络 I/O 在锁外**：
```go
func (s *taskClientStream) consume() {
    s.mu.Lock()
    needMore := len(s.queue) < PrefetchLimit
    s.mu.Unlock()  // ← 解锁后执行 I/O
    
    if needMore {
        entry := <-s.subscription  // 锁外订阅
        
        s.mu.Lock()
        s.queue = append(s.queue, entry)
        s.mu.Unlock()
    }
}
```

✅ **优点**：
- 避免持锁等待网络
- 提高并发吞吐量

**性能验证**：
```bash
✅ TestReviewConcurrentStreamingCost  # 并发流测试通过
✅ go test -race 全部通过
```

## 三、性能问题与优化机会

### 3.1 序列化开销 ⚠️ **可优化 (3/5)**

**问题 1：每帧多次序列化**

**当前流程**（internal/wire/log_codec.go）：
```go
func (c *FrameCodec) Encode(ctx, method, frame) ([]byte, error) {
    // 1. 序列化原始帧
    data, _ := proto.Marshal(frame)  // ← 第一次
    
    // 2. 通过 codec 链
    for _, codec := range c.chain {
        data, _ = codec.Encode(ctx, method, data)  // ← 可能包含压缩/加密
    }
    
    // 3. 包装为最终 envelope
    envelope := &EncodedLogFrame{Payload: data, ...}
    return proto.Marshal(envelope)  // ← 第二次
}
```

**开销分析**：
- 每个 DATA 帧至少 2 次 protobuf 序列化
- 如果有压缩/加密 codec，开销更大
- 每次分配新 []byte，无复用

**影响**：
- 高吞吐场景下 CPU 和 GC 压力
- 每秒 1000 帧 = 2000+ 次序列化

**建议优化**：
```go
// 优化 1：使用 sync.Pool 复用缓冲区
var bufferPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func (c *FrameCodec) Encode(...) ([]byte, error) {
    buf := bufferPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()
        bufferPool.Put(buf)
    }()
    
    // 使用 buf 进行序列化
}

// 优化 2：对于不变帧（CLAIM），缓存编码结果
type FrameCodec struct {
    claimCache map[string][]byte  // nonce → 编码结果
}
```

**预期收益**：
- 减少 30-50% 序列化开销
- 降低 GC 压力

---

**问题 2：envelope 序列化开销**

**当前流程**（internal/wire/envelope.go）：
```go
func Encode(ctx, method, message, ...) (Envelope, error) {
    // 1. ProtoJSON 序列化业务消息
    data, _ := protojson.Marshal(message)  // ← CPU 密集
    
    // 2. 通过 codec 链
    for _, codec := range chain {
        data, _ = codec.Encode(ctx, method, data)
    }
    
    // 3. base64 编码（JSON 兼容）
    envelope.Payload = base64.StdEncoding.EncodeToString(data)
    
    // 4. JSON 序列化整个 envelope
    return json.Marshal(envelope)  // ← 第二次
}
```

**开销分析**：
- ProtoJSON 比 protobuf 慢 3-5 倍
- base64 编码增加 33% 大小
- JSON 序列化再次遍历

**影响**：
- 每次任务提交都触发
- 输入越大，开销越明显

**是否可优化**：
- ⚠️ ProtoJSON 是协议要求（v4），不能改为 protobuf
- ⚠️ base64 是 JSON 兼容性要求
- ✅ 可以缓存不变的 envelope 元数据部分

**建议优化**：
```go
// 缓存重复的 envelope 元数据
type EnvelopeCache struct {
    metadata map[string][]byte  // method → 元数据 JSON
}

// 分离元数据和载荷的序列化
```

**预期收益**：有限（10-20%），因为载荷仍需每次序列化

### 3.2 内存拷贝 ⚠️ **可优化 (3/5)**

**问题：较多的 Clone 操作**

**统计结果**：
```bash
proto.Clone:  3 处
maps.Clone:   6 处
```

**关键位置**：

**位置 1：状态机保存结束帧**（internal/stream/log.go:96）：
```go
case "ATTEMPT_END":
    s.End = proto.Clone(frame).(*wire.LogFrame)  // ← 深拷贝
```

**原因**：防止外部修改影响状态机
**开销**：每次执行 1 次，可接受

**位置 2：元数据传递**（internal/backend/run.go:425）：
```go
values = maps.Clone(values)  // ← 拷贝 map
```

**原因**：避免并发写冲突
**开销**：每次调用 1 次，map 通常较小

**位置 3：执行信息传递**（多处 AdditionalMetadata）：
```go
info.AdditionalMetadata = maps.Clone(info.AdditionalMetadata)
```

**原因**：传递给多个 goroutine
**开销**：累积可能显著

**是否可优化**：
- ⚠️ Clone 是正确性保证，不能简单删除
- ✅ 可以考虑 copy-on-write 模式
- ✅ 可以使用不可变数据结构

**建议优化**：
```go
// 方案 1：仅在必要时 Clone
func (s *State) Apply(frame *LogFrame) {
    if needToSave {
        s.End = proto.Clone(frame).(*wire.LogFrame)
    } else {
        // 只读引用，不 Clone
    }
}

// 方案 2：使用不可变 map 包装
type ImmutableMap struct {
    data map[string]string
}
// 修改时才 Clone，读取直接引用
```

**预期收益**：
- 减少 20-30% 内存分配
- 降低 GC 压力

### 3.3 缺少对象池 ⚠️ **可优化 (3/5)**

**问题：高频分配无复用**

**统计结果**：
```bash
项目中无 sync.Pool 使用
```

**高频分配点**：

**位置 1：帧编解码**：
```go
// 每次编码都分配新 LogFrame
frame := &wire.LogFrame{
    Kind: "DATA",
    OutputSeq: seq,
    Payload: data,
}
```

**位置 2：缓冲区分配**：
```go
// 序列化时分配临时缓冲
data, _ := proto.Marshal(frame)  // 内部分配
```

**位置 3：队列元素**：
```go
s.queue = append(s.queue, bufferedOutput{
    frame: frame,
    cursor: cursor,
})
```

**影响**：
- 高吞吐场景下 GC 频繁
- 每秒 1000 帧 = 1000+ 次分配

**建议优化**：
```go
// 帧对象池
var framePool = sync.Pool{
    New: func() any {
        return &wire.LogFrame{}
    },
}

func encodeFrame(...) []byte {
    frame := framePool.Get().(*wire.LogFrame)
    defer framePool.Put(frame)
    
    // 使用 frame
    frame.Kind = "DATA"
    // ...
}

// 缓冲区池
var bufferPool = sync.Pool{
    New: func() any {
        return make([]byte, 0, 4096)
    },
}
```

**预期收益**：
- 减少 40-60% 内存分配
- 降低 GC 延迟
- 提高高吞吐场景性能

### 3.4 CLAIM 读回延迟 ⚠️ **可优化 (4/5)**

**问题：竞争场景下的等待时间**

**当前流程**（internal/stream/claim.go）：
```go
func (c *ClaimManager) Acquire(ctx) (Outcome, error) {
    // 1. 发布 CLAIM
    publish(claimFrame)
    
    // 2. 订阅读回
    for {
        entry := <-c.subscription
        frame := decode(entry)
        
        if frame.Kind == "CLAIM" && frame.Epoch == c.epoch {
            if frame.Writer == c.nonce {
                return Owned, nil
            } else {
                return Lost, nil
            }
        }
    }
}
```

**延迟分析**：
- 发布延迟：网络 RTT（通常 5-50ms）
- 订阅延迟：取决于 Streams 实现（可能 10-100ms）
- 总延迟：设计文档承诺 <10 秒（ClaimTimeout）

**实际测量**（P0 报告）：
- ✅ 并发 CLAIM 竞争测试通过
- ✅ 无明确的延迟报告，说明在可接受范围内

**是否可优化**：
- ⚠️ 依赖 Hatchet Streams 延迟，SDK 无法优化
- ✅ 可以添加本地缓存，避免重复订阅

**建议优化**：
```go
// 优化：批量读回
func (c *ClaimManager) Acquire(ctx) (Outcome, error) {
    // 一次订阅读取多个 entry，减少系统调用
    batch := <-c.subscription  // 批量返回
    for _, entry := range batch {
        // 处理
    }
}
```

**预期收益**：有限，因为主要受限于后端

### 7.2 中优先级（v0.3.0 考虑）

**3. 减少 Clone 操作**
```go
// 使用 copy-on-write 模式
type CowMap struct {
    data map[string]string
    refs int32
}

func (m *CowMap) Clone() *CowMap {
    atomic.AddInt32(&m.refs, 1)
    return m  // 共享引用
}

func (m *CowMap) Modify(key, value string) *CowMap {
    if atomic.LoadInt32(&m.refs) > 1 {
        // 有其他引用，需要真正 Clone
        return &CowMap{data: maps.Clone(m.data)}
    }
    // 独占引用，直接修改
    m.data[key] = value
    return m
}
```

**预期收益**：
- 减少 20-30% 内存拷贝
- 适用于读多写少的场景

**实施成本**：较高，需要重构数据传递模式

**4. 优化序列化路径**
```go
// 缓存不变的编码结果
type FrameCodec struct {
    // 缓存 CLAIM 编码（每次执行只需一次）
    claimCache sync.Map  // nonce → []byte
}

func (c *FrameCodec) Encode(frame *LogFrame) []byte {
    if frame.Kind == "CLAIM" {
        if cached, ok := c.claimCache.Load(frame.Writer); ok {
            return cached.([]byte)
        }
    }
    
    // 正常编码
    data := encodeFrame(frame)
    
    if frame.Kind == "CLAIM" {
        c.claimCache.Store(frame.Writer, data)
    }
    
    return data
}
```

**预期收益**：
- 减少 CLAIM 编码开销
- 每次执行节省 1 次序列化

**实施成本**：中等，需要管理缓存生命周期

- **原因**：每帧多次序列化
- **影响**：CPU 使用率高
- **缓解**：批量操作分摊成本
- **建议**：添加性能监控

- **影响**：任务启动延迟
- **缓解**：10 秒超时保护
- **建议**：监控实际延迟
