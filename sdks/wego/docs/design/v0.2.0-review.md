## 三、协议细节评估

### 3.1 输出完整性判定 ✅ **改进显著**

**修订版策略（第 6.5 节）**：
```
运行观察器从调用开始就工作：订阅通知 + 默认 1 秒状态轮询
CompletionTimeout 从权威终态确认后开始（30 秒）
```

对比原评审建议：
```
原建议：30 秒无消息后查询 TaskRun 终态
修订版：持续观察 + 终态后对账预算
```

✅ **修订版更优**：
- 不等 30 秒空闲才检查取消（避免误杀长任务）
- 从调用开始就观察状态（及时响应控制台取消）
- 终态确认后才启动对账超时（明确两个阶段）

**六种情况处理表**（第 6.5 节）：
- ✅ attempt 结束但运行可能重试 → 继续观察
- ✅ 引擎成功 + 结束帧 + 全部输出 → EOF
- ✅ 引擎成功但缺结束帧 → 在 CompletionTimeout 内续读
- ✅ 引擎取消 → 返回 Canceled，不等结束帧
- ✅ 引擎失败有结束清单 → 交付前缀 + 返回错误
- ✅ 引擎失败无结束清单 → 返回失败 + 输出未完全对账信息

**评估**：原评审的"补充项 4"已完全解决，且策略优于原建议。

---

### 3.2 历史起点与保留期 ✅ **保守合理**

**保守规则（第 5.4 节）**：
```
需要看到 epoch=0 的初始 CLAIM，验证全部有效序号
若初始 CLAIM 已不可读，返回历史不可恢复错误
```

**限制场景**：
```
最初投递在建立 CLAIM 前就丢失，随后直接收到更高 epoch
→ 明确失败，不静默当首次执行
```

✅ **正确的设计决策**：
- 正确性优先于可用性
- P0 必须记录这一限制（已在 P0-09 中）
- 明确未来改进路径："另行评审可持久验证的日志起点机制"

**评估**：这是一个诚实的设计约束，比"静默从剩余历史开始"的错误行为好得多。

---

### 3.3 启动屏障修正 ✅ **关键修正**

**原评审错误**：
```go
// 原评审伪代码：
cursor, _ := m.backend.PublishEvent(ctx, broadcastTopic, joinMsg)
m.broadcastSub = m.backend.Subscribe(ctx, broadcastTopic, cursor)
```

**修订版正确流程（第 7.2 节）**：
```
1. 建立订阅（从历史最早或已验证游标）
2. 发布 JOIN marker
3. 从历史读取直到各自 marker，保存 marker 的实际 cursor
4. 从 marker 后继续消费
```

✅ **修订版正确理由**：Publish 不返回 cursor（第 1.3 节表格），必须订阅读回。

**成本与限制（第 7.2 节）**：
- ✅ 启动屏障总预算：30 秒
- ✅ 扫描上限：10 万帧 / 64 MiB
- ✅ 超限明确失败，不假装扫描成本不存在
- ✅ 部署需控制事件保留期和广播量

**评估**：修订版纠正了原评审的理解错误，并明确了成本约束。

---

### 3.4 Realtime 的诚实限制 ✅ **诚实设计**

**明确限制（第 6.6 节）**：
```
- 使用 PutStream，没有持久回放
- 先建立订阅等待就绪，仍不能消除断开丢失风险
- 若官方接口无法证明订阅就绪，P0 必须记录该限制
- 断流不重新执行任务以"补齐"输出
- 禁止配置可能重复实时输出的应用重试
```

✅ **诚实的保证边界**：不宣称 Realtime 能完整传输，明确其限制和适用场景。

**评估**：这是负责任的设计，避免过度承诺。
